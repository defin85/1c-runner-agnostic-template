## Context

Шаблон поставляет проектам overlay: пути из `automation/context/template-managed-paths.txt` перезаписываются при `make template-update`. Проект `tn-bp30-sdd` изменял часть этих путей у себя. Если выполнить в нём обновление раньше, чем эти правки попадут в шаблон, они потеряются. Поэтому порядок работ жёсткий:

1. Перенести правки и инструменты в шаблон.
2. Выпустить версию шаблона.
3. Выполнить `template-update` проекта отдельным change в проекте.

Для необязательных материалов в шаблоне уже есть подходящий образец — `init-test-tooling` из `reusable-testing-tooling`:

- заготовки лежат в template-managed каталоге и обновляются overlay;
- явная команда копирует их в project-owned каталог;
- если целевой каталог существует, команда ничего не меняет.

Этот change переиспользует тот же образец и не вводит новый механизм.

## Goals / Non-Goals

**Goals:**

- Базовый инструментарий работает в любом созданном проекте без сведений о конкретном заказчике.
- Необязательные модули включаются явно, не мешают проектам без удалённой площадки или миграции и не перезаписывают project-owned данные при обновлении.
- Каждый перенесённый исполняемый слой имеет smoke-проверку, которая работает без 1С.
- Проект-источник может обновиться без потери своих доработок.

**Non-Goals:**

- Перенос прикладных правил КД, сценариев волн и матриц счетов.
- Перенос сведений о площадке заказчика.
- Универсальная поддержка всех VDI-клиентов. Поставляется адаптер для клиента Citrix Workspace. Контракт ввода и передачи файлов не зависит от клиента.
- Замена существующего PostgreSQL golden-контура шаблона. Модуль КД использует его.

## Decisions

### D1. Базовый набор и необязательные модули

Базовый набор составляют:

- наблюдение длительных операций на Linux и Windows;
- штатный запуск клиента `run-client`;
- проверка BSL;
- CLI метаданных вместо импортированных `meta-*`, `form-*` (кроме `form-patterns`) и `cfe-borrow` (Р6), конвертация обычных форм, `v8unpack`, `v8std`;
- поисковый регламент;
- проверка путей навыков;
- basedpyright gate.

Эти инструменты не зависят от площадки и предметной миграции.

Площадка и КД 2.1 поставляются как необязательные модули `automation/optional/<module>/`. Команда `make optional-module-init MODULE=<module>` копирует их в project-owned пути:

| Модуль | Каталоги | Навыки |
|---|---|---|
| площадка | `infra/site/`, `docs/infra/site/` | `.agents/skills/site-*` |
| КД 2.01 | `migration/kd21/` (профили, сценарии, обработка выгрузки структуры `metadata-exporter`), `docs/agent/kd21-rules-workbench-runbook.md` | `1c-prepare-manual-migration-bases` |

Команда регистрирует материализованные пути как project-owned в preserve-контракте. Команда `init-test-tooling` подтвердила этот образец: overlay обновляет заготовки, но не материализованные копии.

**Альтернатива:** вопрос Copier. Отклонена как рекомендуемая: её трудно применить к уже созданным проектам, и она делает поведение `copy` и `update` разным. Выбор подтверждён пользователем (решение Р1).

### D2. Исполняемый код необязательных модулей

Исполнитель КД `scripts/migration/kd-rules-cycle`, ядро компилятора `scripts/migration/kd_xml_compiler/` и общий код обёрток площадки на стороне оператора остаются template-managed в `scripts/`. Проектам без модуля они не мешают: без материализованного профиля и сценария команда завершается с понятной ошибкой.

В project-owned путь копируются только:

- профили, сценарии, регламенты и навыки, которые проект будет дописывать;
- серверные обёртки площадки. Их устанавливают на чужие серверы с машинной сверкой SHA-256, поэтому проект должен фиксировать установленные байты у себя.

Так исправления исполнителя приходят проектам обычным обновлением.

### D3. Обезличивание

- В шаблон не попадают имена серверов, домены, IP, CIDR, UUID баз и кластеров, имена баз заказчика, учётные записи, итоги операций по базам, пути хоста разработчика.
- Файлы переименовываются: `tnl-*` → `site-*`.
- Сведения, привязанные к площадке, задаются только через project-owned `*.json` профили. Их примеры с вымышленными значениями лежат в заготовке.
- Smoke `customer-site-deidentified.sh` ищет в поставляемых путях запрещённые шаблоны: IPv4, UUID вне закреплённых фикстур, известные проектные имена. Это проверка публикационной границы, а не семантики кода.

### D4. Наблюдение как единая точка

`1c-observe-run` и общий адаптер наблюдения становятся обязательным слоем всех обёрток, запускающих клиент или Designer, включая `run-client`.

В проекте адаптер встроен в template-managed файлы: `scripts/lib/capability.sh` (`run_observed_command`, Linux) и `scripts/python/runtime.py` (`observe-command`, Windows, вызывается из Bash через `run-python.ps1`). В шаблоне `runtime.py` уже разделён на модули `runtime_*`. Поэтому Windows-часть переносится в отдельный модуль `runtime_*` (рабочее имя `runtime_observation.py`), а не копированием `runtime.py`.

Остановка при неизменном прогрессе (Р7) — новое поведение. В проекте общий адаптер только пишет возраст прогресса `stageAgeSeconds` в heartbeat. Останавливает процесс лишь исполнитель КД (`stall_timeout` в `kd_cycle_common.run`, порог из лимита профиля `runtimeStageTimeoutSeconds`). В шаблоне порог передаёт вызывающая обёртка. Если порог не задан, адаптер не останавливает операцию. Исполнитель КД передаёт адаптеру свой `runtimeStageTimeoutSeconds` и не держит отдельного цикла ожидания.

Разовый launcher, ручной cursor или увеличенный timeout не считаются заменой. Технологический журнал включается только ограниченным `logcfg.xml` на время конкретного запуска через operation cursor. Постоянные события `CALL`, `SCALL`, `SDBL`, SQL и `SYSTEM` не включаются.

### D5. Проверка BSL без теневых парсеров

Проверка BSL маршрутизируется только в авторитетные инструменты:

- `bsl-analyzer` `check` с точным подключением;
- выборочная платформенная компиляция `check-cf-modules.sh`;
- Designer `CheckModules`.

Python- и shell-тесты проверяют маршрутизацию, выбор файлов и формат результата, но не синтаксис. Если авторитетная проверка недоступна, результат фиксируется как `синтаксис: не проверен`.

### D6. Модуль КД 2.01 — ядро компилятора и минимальный исполнитель

С 2026-10-05 проект собирает правила без 1С (flow-4, шаги 3–4). База КД `kd_21_work`, `КД21Исполнитель.epf`, перехватчик времени `onec_fixed_time.c` и Xpra-сборка удалены. Исполнитель разделён на модули `kd_cycle_*` (шаг 7). Поэтому модуль шаблона строится по этой схеме (Р5), а не по схеме proposal от 2026-09-27.

**Ядро компилятора** `scripts/migration/kd_xml_compiler/`:

- нейтральная модель метаданных: объекты, реквизиты, табличные части, типы;
- модель правил и сериализатор КД 2.01: правила конвертации объектов и свойств, выгрузки, очистки, регистрации, глобальные обработчики и параметры;
- детерминированный порядок элементов и правил регистрации, чтобы повторная сборка давала побайтно те же XML и ZIP;
- адаптер XML структуры метаданных КД. Структура выгружается из живой базы обработкой `metadata-exporter` и закрепляется в сценарии по SHA-256 (`inputs.sourceStructure`, `inputs.targetStructure`).

Ядро MUST NOT импортировать проектные модули; границу проверяет тест. Наложение CFE, построение правил из сценариев конкретных конфигураций и шаблоны текстов обработчиков остаются проектным слоем. Перед переносом нужно проверить, что `metadata_catalog.json.gz` пакета не содержит сведений заказчика, либо заменить его фикстурой.

**Исполнитель** реализует:

- стадии `doctor`, `reset`, `build`, `load`, `run`, `verify`; `build` вызывает компилятор, `load` загружает правила в обе расходуемые базы штатной обработкой;
- отдельную сборку выпуска без баз `run build-rules` со статусом `rules-built`;
- формат `scenario.json`, `state.json` версии 2, `result.json`, манифест выпуска;
- блокировку профиля;
- требование нового `run-root` после изменения входов.

Стадия `reset` восстанавливает две расходуемые базы (источник и приёмник) из PostgreSQL golden-снимков существующего контура шаблона. Она отказывает, если имя цели совпадает с именем эталонной базы или отсутствует в списке расходуемых баз профиля.

Прикладные стадии проекта подключаются как расширения сценария через объявленные узлы с зависимостями. Исполнитель не содержит их логики. Из 23,6 тыс. строк `kd_rules_cycle.py` и `kd_cycle_*.py` проекта в шаблон попадают только общие части `kd_cycle_state`, `kd_cycle_validation`, `kd_cycle_cli` и `kd_cycle_common` после удаления проектных имён.

### D7. Порядок переноса правок template-managed файлов

Для каждого из 181 расходящегося файла (сверка 2026-10-08, коммит проекта `46c814b51`) и для 70 путей, которые проект убрал из своего `template-managed-paths.txt`, нужно:

1. Взять diff проекта относительно `v0.3.36`.
2. Отделить общие исправления от проектных.
3. Наложить общие исправления на текущий `HEAD` шаблона. Для `runtime.py` — на соответствующие модули `runtime_*`.

Проектные фрагменты, которые нельзя обобщить, переносятся в project-owned точки расширения (`project-specific baseline extension slot`, локальные профили), а не в шаблон.

Результат сверки фиксируется в `inventory.md` этого change: файл, решение (`перенести|обобщить|оставить в проекте|уже есть|вывести`), причина. Решение `вывести` применяется к удалённым из списка путям импортированных редакторов метаданных (Р6).

Проект продолжает меняться: после proposal 29 расходящихся файлов изменились снова. Поэтому `inventory.md` фиксирует коммит проекта, на котором выполнена сверка. Перед этапом 3.3 сверку нужно повторить для файлов, изменённых после этого коммита.

## Bootstrap и update

- **`copier copy`:** базовый инструментарий и заготовки `automation/optional/*` попадают в проект. Необязательные модули не материализуются.
- **`template-update`:** базовый инструментарий и заготовки обновляются. Материализованные каталоги модулей, профили, сценарии, доказательства и кеши (`.artifacts/v8std`, run-root) не изменяются.
- **`make optional-module-init`:**
  - если хотя бы один целевой путь существует, завершается с ошибкой без изменений;
  - при ошибке копирования удаляет всё скопированное в этом запуске.
- **Проект-источник:** после релиза выполняет `template-update`. Затем инициализирует модули и переносит в материализованные каталоги свои площадочные и КД-материалы отдельным change в проекте.

## Risks / Trade-offs

- **Объём.** Change большой. Реализация разбита на этапы в `tasks.md`; каждый этап проходит smoke и может быть выпущен отдельно.
- **Утечка сведений заказчика.** Её предотвращают smoke-проверка обезличивания и ручное ревью списка поставляемых путей перед релизом.
- **Метод `v8users`.** Он прямо меняет служебные таблицы СУБД. Поставляется отдельной опцией модуля (решение Р2), с обязательной резервной копией и проверкой возврата.
- **Ветка change отстала от `origin/main`.** В `origin/main` есть `unify-agent-skill-sources`: `.claude/skills` строится командой `make sync-claude-skills`, а `imported_skills.py` переписан. До реализации ветку нужно перенести на `origin/main`, иначе задачи 2.x и 7.2 будут конфликтовать.
- **Проект-источник продолжает меняться.** Правки после коммита сверки не попадут в шаблон без повторной сверки (D7).
- **Расхождение `runtime.py`.** Шаблон уже разделил модуль. Перенос правок требует ручного сопоставления; smoke существующего runtime-контура обязателен.
- **Нагрузка на лёгкий CI.** basedpyright добавляет время; gate работает по baseline и не требует исправления всего существующего кода сразу.

## Принятые решения

Пользователь 2026-09-27 согласился с рекомендациями proposal.

- **Р1. Включение модулей.** Только командой `make optional-module-init MODULE=<имя>` по образцу `init-test-tooling`. Вопрос Copier не добавляется. Последствие: уже созданные проекты включают модули той же командой, поведение `copy` и `update` одинаково.
- **Р2. Восстановление доступа через `v8users`.** Обёртка поставляется в модуле площадки отдельной опцией: регламент с предупреждением о недокументированном методе, порядок `backup → hide → restore → verify`, отказ `hide` без копии. Последствие: задача 5.4 выполняется с включением обёртки; смок-проверка отказа обязательна.
- **Р3. Исполнитель КД 2.1.** В шаблоне пишется минимальное ядро по D6; проектный `kd_rules_cycle.py` целиком не переносится. Последствие: проект-источник после обновления переводит свои прикладные стадии на узлы-расширения отдельным change. Стадию `build` уточняет Р5.
- **Р4. Порядок выпуска.** Этапы 0–3 и 7 для базового набора выпускаются отдельной версией шаблона до этапов 4–6. Последствие: проект-источник может выполнить `template-update` для базового набора раньше, сохранив площадочные и КД-материалы у себя до выпуска модулей.

### Актуализация 2026-10-08

Сверка с проектом-источником на коммите `46c814b51` выполнена 2026-10-08. С момента proposal в проекте появилось 669 коммитов. Пользователь 2026-10-08 выбрал рекомендованные варианты:

- **Р5. Модуль КД 2.1 строится вокруг ядра компилятора.** Шаблон поставляет нейтральное ядро `kd_xml_compiler`: модель метаданных, сериализатор КД 2.01, адаптер XML структуры КД и обработку выгрузки структуры. Исполнитель работает с двумя расходуемыми базами: источником и приёмником. База КД, `КД21Исполнитель.epf` и Xpra-сборка не поставляются. Последствия: заменяет Р3 в части стадии `build`. Наложение CFE, сценарии БП и шаблоны текстов обработчиков остаются в проекте.
- **Р6. Импортированные `meta-*`, `form-*` (кроме `form-patterns`) и `cfe-borrow` выводятся из шаблона.** Их заменяет CLI `metadata`. Последствия: `sync-imported-skills` пропускает эти навыки, а созданные проекты теряют их при `template-update`. Для этого нужна запись в release notes.
- **Р7. Остановка при неизменном прогрессе становится новым поведением общего адаптера.** В проекте её реализует только исполнитель КД (`stall_timeout`). Порог передаёт вызывающая обёртка, по умолчанию остановка выключена. Последствия: код переносится из `kd_cycle_common.run` в общий адаптер, исполнитель КД использует общий адаптер.
- **Р8. В базовый набор входят `1c-run-client` и Windows-наблюдение `observe-command`.** Запуск через PiP Child session (`add-windows-pip-1c-techlog`) не входит, пока change проекта не заархивирован.
- **Р9. Линтер и форматирование Python — ruff (решение 2026-10-08).** `ruff check` с правилами `E4`, `E7`, `E9`, `F`, `B`, `I`, `UP`, `target-version = "py312"`, `line-length = 120`. Для серверных обёрток модуля площадки задаётся `per-file-target-version = "py37"`, чтобы `UP` не предлагал синтаксис, недоступный системному Python площадки. `ruff format` использует ту же длину строки. Правила не отключаются ради удобства, каждый `noqa` содержит причину. Код пишется так, чтобы `ruff check --fix` не менял поведение: после автоисправлений unit-тесты проходят. Настройки лежат в template-managed `ruff.toml`, а не в `pyproject.toml`, чтобы `pyproject.toml` созданного проекта не конфликтовал с обновлением шаблона. Последствия: задача 3.2 расширяется; перенесённый код сразу проходит линтер. Замер 2026-10-08: в шаблоне 61 замечание (42 автоисправимых) и 25 файлов для форматирования; в переносимых модулях проекта — 78 замечаний и 18 файлов.
- **Р10. basedpyright в режиме `standard` без baseline (решение 2026-10-08).** Файлы baseline и `type-check-update-baseline.*` не поставляются; если baseline-файл есть, проверка завершается ошибкой. Последствия: около 150 ошибок шаблона (замер 2026-10-08 во временном конфиге) исправляются кодом в задаче 3.2; проект-источник уже проходит этот режим без ошибок (`basedpyright-baseline-count.json`: 0).
- **Р11. Импортированные `db-*` и `epf/erf-*` работают только через runtime-профиль (решение 2026-10-08).** Запуск идёт через профиль и ibcmd без перехода на Designer. `db-run` перенаправляется на `run-client`, сборка EPF/ERF выполняется через `file-import`, пароль в выводе скрыт. Правки 21 vendor-файла `cc-1c-skills` не копируются: это поведение реализуется в `imported_skills.py` при генерации навыков, иначе `sync-imported-skills` его сотрёт. Проектный `scripts/python/onec_xpra.py` переносится вместе с `run-client` (задача 1.5). Последствия: проекты без runtime-профиля теряют прямой запуск импортированных навыков через Designer; это фиксируется в release notes.
- **Р12. Возможности из расходящихся template-managed файлов входят в базовый набор (решение 2026-10-08).** Это `--override-unsupported-profile`, `--vendor-cf`, `--info-only`, регистрация ИБ в кластере через `rac` после `create-ib`, флаги безопасности CFE, Designer-драйвер `manage-cfe`, парная проверка Linux/Windows и `one-c-form-viewer`. Последствия: каждая переносится в задаче 3.3 с проверкой; в HEAD шаблона они реализуются в Python-runtime, а не копированием shell-кода проекта.
- **Р13. Хранилище артефактов вне checkout входит в этот change (решение 2026-10-08).** Переносится `scripts/python/artifact_storage.py` с обёрткой `scripts/artifact-storage` и тестами: общий каталог `<repo>-artifacts` рядом с репозиторием, паспорта прогонов, проверка лимитов размера и свободного места до создания прогона, явная очистка `prune`. Проектный модуль работает только на Linux (`fcntl`, `os.statvfs`). В шаблоне блокировка строится на `runtime_lock`, чтобы хранилище работало и на Windows. Последствия: новая задача 2.8 и требование в `onec-development-toolkit`.
- **Р14. Из шаблона удаляются тексты, которые проект уже убрал (решение 2026-10-08).** Это тесты EPF, проверяющие текст BSL (`test_epf_templates_form_title_version.py` и текстовые проверки в `test_epf_init_from_template_command.py`, по D5), блок `rlm-tools` в `agents-overlay.sh`, а также `format-bsl.sh|.ps1` с целью `format-bsl`. Последствия: созданные проекты теряют рекомендацию MCP `rlm-tools` и форматирование BSL через BSL LS; это фиксируется в release notes.
- **Р15. Python-конфигурация созданного проекта принадлежит проекту (решение 2026-10-08).** `pyproject.toml`, `uv.lock` и `pyrightconfig.json` шаблон кладёт в проект один раз при создании, затем они входят в preserve-контракт, и `template-update` их не перезаписывает. Версии `ruff`, `basedpyright` и `pytest` проверяет `type_checking.py`: он требует нужные пины в `requirements-dev.txt`, совпадение этого файла с `uv export` и печатает команду исправления. Проектный `pyrightconfig.json` подключает template-managed базовый конфиг через `extends`. Ослабить режим, отключить правило или задать baseline проверка не даёт. Последствие: проект может добавлять свои зависимости и корни проверки типов, а шаблон обновляет требования к инструментам через проверку, не трогая файлы проекта.
- **Р16. Записи платформ в таблице поддержки сред существующего проекта добавляет явная команда миграции (решение 2026-10-10).** Проверка документации созданного проекта требует для каждой команды `platforms.linux` и `platforms.windows` в `automation/context/runtime-support-matrix.json`. Таблица создаётся один раз и принадлежит проекту, поэтому у проектов, созданных до этого change, таких записей нет. Шаблон поставляет команду миграции по образцу `migrate-runtime-profile-v3`: она дописывает только отсутствующие записи платформ со статусом «не проверено», существующие поля не меняет, Markdown-версию таблицы пересобирает из JSON. `template-update` таблицу проекта не меняет. Проверка при отсутствии записей падает и в сообщении называет эту команду.
- **Р17. Один выпуск шаблона после всего change; Р4 в части отдельного выпуска отменено (решение 2026-10-10).** Этапы по-прежнему выполняются в порядке 0–3, 7, затем 4–6, но промежуточный тег не ставится: один тег после закрытия этапа 8. Ветку `codex/import-project-toolkit` разрешено отправлять в удалённый репозиторий без PR и без изменения `main`, чтобы Windows-задание CI проверило `make.ps1`, PowerShell-обёртки и Windows-путь `template-update`. После закрытия всех задач change архивируется через `openspec archive` отдельным коммитом.
- **Р18. Конфигурация ruff принадлежит проекту так же, как конфигурация basedpyright по Р15 (решение 2026-10-10).** Общие правила (`E4`, `E7`, `E9`, `F`, `B`, `I`, `UP`, `target-version = "py312"`, длина строки 120) переносятся в template-managed `scripts/qa/ruff-base.toml`. `ruff.toml` создаётся один раз со строкой `extend = "scripts/qa/ruff-base.toml"` и дальше принадлежит проекту: проект добавляет свои `exclude` и `per-file-ignores`. Проверка падает, если `ruff.toml` не расширяет базу или убирает правила базы для файлов из манифеста шаблона.
- **Р19. `make analyze-bsl` работает только через MCP `bsl-analyzer`; BSL LS из шаблона удаляется (решение 2026-10-10).** Пользователь: «BSL LS вообще не используем». Из проекта-источника переносится MCP-клиент `analyze-bsl` (`_analyze_bsl_standalone` и запуск процесса MCP с остановкой дерева процессов на Windows) в обезличенном виде: без проектных идентификаторов в реестре исключений, без проектного каталога исходников по умолчанию. Запуск jar BSL LS, его загрузка и настройки удаляются из шаблона вместе с тестами и упоминаниями в документации и навыках; если `bsl-analyzer` не настроен, команда завершается с понятной ошибкой и указанием на `docs/agent/bsl-analyzer-workspace-runbook.md`.
- **Р20. Поколение расходуемых баз определяется `generationId`, а не UUID баз (решение координатора 2026-10-10).** Восстановление из PostgreSQL golden-снимка не меняет UUID информационной базы, поэтому сравнение поколений по UUID не отличает новое поколение от прежнего. Стадия `reset` выдаёт новый `generationId` для каждой пары баз; `--baseline-result` с тем же `generationId` завершается статусом `failed` и причиной `same generation`.
