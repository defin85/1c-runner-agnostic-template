## ADDED Requirements

### Requirement: Каждый запуск клиента и Designer наблюдается общим адаптером

Штатные обёртки шаблона, которые запускают клиент 1С или Designer, MUST выполнять запуск через общий адаптер наблюдения. Это относится к `direct-platform.sh`, `db-run`, EPF/ERF build/dump и операциям с временными файловыми ИБ. Адаптер MUST записывать в `<run-root>/observation.jsonl` события schema v1: одно `started`, heartbeat не реже заданного интервала и ровно одно terminal-событие `completed` или `failed`.

#### Scenario: Успешный запуск Designer

- **WHEN** обёртка выполняет операцию Designer, которая завершилась с кодом 0
- **THEN** `observation.jsonl` содержит одно событие `started`, не менее одного heartbeat при длительности больше интервала и ровно одно событие `completed`
- **AND** `summary.json` содержит terminal-секцию с кодом завершения и путём к журналу

#### Scenario: Процесс завершился без машинного результата

- **WHEN** процесс клиента завершился, но ожидаемый файл результата операции отсутствует
- **THEN** адаптер записывает terminal-событие `failed` с причиной отсутствия результата
- **AND** обёртка возвращает ненулевой код

### Requirement: Операция без прикладного прогресса останавливается

Если операция объявляет файл прикладного прогресса, адаптер MUST остановить её процессную группу, когда содержимое этого файла не меняется дольше `runtimeStageTimeoutSeconds`. Общий timeout по времени выполнения MUST NOT применяться к таким операциям.

#### Scenario: Прогресс перестал меняться

- **WHEN** содержимое файла прогресса не менялось дольше `runtimeStageTimeoutSeconds`
- **THEN** адаптер завершает процессную группу операции
- **AND** записывает terminal-событие `failed` с причиной `stalled` и последним значением прогресса

#### Scenario: Долгая операция с меняющимся прогрессом

- **WHEN** операция длится дольше любого фиксированного интервала, но файл прогресса продолжает меняться
- **THEN** адаптер не прерывает операцию

### Requirement: Технологический журнал включается только на время точного запуска

Сценарий `scripts/diag/technological-log.sh` MUST включать технологический журнал ограниченной конфигурацией на время одного запуска и выдавать operation cursor этого запуска. Сценарий MUST NOT включать постоянные события `CALL`, `SCALL`, `SDBL`, SQL и `SYSTEM`. Он MUST восстанавливать исходный `logcfg.xml` после завершения или ошибки запуска.

#### Scenario: Чтение журнала по cursor

- **WHEN** агент читает технологический журнал по operation cursor завершённого запуска
- **THEN** выдаются только записи в интервале этого запуска
- **AND** исходный `logcfg.xml` совпадает побайтно с состоянием до запуска

#### Scenario: Запуск завершился ошибкой

- **WHEN** наблюдаемая операция завершилась ошибкой или была прервана
- **THEN** исходный `logcfg.xml` всё равно восстановлен
- **AND** cursor позволяет прочитать записи ошибки

### Requirement: Навык наблюдения задаёт порядок диагностики

Навык `1c-observe-run` MUST описывать порядок диагностики зависания:

1. live heartbeat родительской обёртки;
2. `observation.jsonl`;
3. terminal-секция `summary.json`;
4. технологический журнал по cursor;
5. журнал регистрации с точным подключением — только для устойчивых lifecycle-событий с идентификатором запуска.

Навык MUST запрещать чтение полной командной строки процесса, которая может содержать параметры авторизации.

#### Scenario: Агент диагностирует зависшую операцию

- **WHEN** агент следует навыку `1c-observe-run` для операции без новых heartbeat
- **THEN** он проверяет источники в порядке, заданном навыком, и не читает командную строку процесса
