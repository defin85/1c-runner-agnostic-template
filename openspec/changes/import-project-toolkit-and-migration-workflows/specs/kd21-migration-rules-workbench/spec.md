## ADDED Requirements

### Requirement: Модуль КД 2.1 материализуется только явной командой

Шаблон MUST поставлять заготовку модуля в `automation/optional/kd21-migration/`. Команда `make optional-module-init MODULE=kd21-migration` MUST копировать в project-owned пути примеры профиля, сценария, матрицы файлов, ожидаемого результата, регламент `docs/agent/kd21-rules-workbench-runbook.md` и навык подготовки баз ручной проверки. Прикладные правила обмена в заготовку MUST NOT входить.

#### Scenario: Инициализация модуля

- **WHEN** выполняется команда инициализации в проекте без каталога `migration/kd21/`
- **THEN** создаётся `migration/kd21/` с примерами `profiles/*.example.json` и `scenarios/technical-workbench/`

### Requirement: Контур изменяет только расходуемые базы профиля

Исполнитель `scripts/migration/kd-rules-cycle` MUST выполнять изменяющие стадии только для баз, перечисленных в профиле как расходуемые: база КД, база-источник, база-приёмник. Стадия `reset` MUST отказывать до любых изменений, если имя цели совпадает с именем эталонной базы профиля или отсутствует в списке расходуемых баз.

#### Scenario: Цель совпадает с эталонной базой

- **WHEN** в профиле имя расходуемой базы-приёмника совпадает с именем эталонной базы
- **THEN** `preflight` завершается ошибкой, и ни одна база не восстанавливается

#### Scenario: Неизменность баз-источников

- **WHEN** прогон завершён
- **THEN** `source-before.json` и `source-after.json` содержат одинаковые идентификаторы и отпечатки эталонных баз

### Requirement: Прогон выполняется по стадиям с одноразовым каталогом результата

Исполнитель MUST выполнять стадии `preflight`, `reset`, `build`, `load`, `run`, `verify` в порядке зависимостей. Он MUST держать блокировку профиля на время прогона и записывать внутреннее состояние в `<run-root>/state.json` версии 2. Если входы сценария изменились относительно состояния в `run-root`, исполнитель MUST отказать с требованием нового `run-root` и стадии `reset`.

#### Scenario: Второй прогон того же профиля

- **WHEN** прогон профиля уже выполняется и запускается второй
- **THEN** второй завершается ошибкой `profile is already running`, не изменяя баз

#### Scenario: Изменились входы

- **WHEN** хеш структуры метаданных в `scenario.json` изменился после первого запуска в том же `run-root`
- **THEN** исполнитель завершается ошибкой `inputs changed; use a new --run-root and reset`

#### Scenario: Ошибка стадии

- **WHEN** стадия `build` завершилась ошибкой
- **THEN** последующие изменяющие стадии не выполняются, а `result.json` имеет статус `failed` с именем стадии

### Requirement: Итог прогона подтверждается машинным результатом и манифестом выпуска

Исполнитель MUST записывать `<run-root>/result.json` со статусом `in-progress`, `failed`, `workbench-run-passed` или `workbench-ready`, поколениями баз и результатами стадий. Он MUST публиковать `release/manifest.json` со списком выпущенных XML и ZIP и их SHA-256. Статус `workbench-ready` MUST выдаваться только при прогоне с `--baseline-result`: второе поколение с другими UUID баз должно побайтно совпасть с первым по всем файлам манифеста.

#### Scenario: Один успешный прогон

- **WHEN** все стадии прошли без `--baseline-result`
- **THEN** `result.json.status` равен `workbench-run-passed`, а манифест содержит SHA-256 каждого файла выпуска

#### Scenario: Выпуск невоспроизводим

- **WHEN** прогон с `--baseline-result` получил отличающийся SHA-256 хотя бы одного файла
- **THEN** статус `failed` с причиной `release hashes differ from baseline generation`

#### Scenario: Поколение не обновилось

- **WHEN** прогон с `--baseline-result` использует базы с теми же UUID поколения, что и базовый результат
- **THEN** статус `failed` с причиной `same generation`

### Requirement: Длительные стадии КД наблюдаются общим адаптером

Каждая блокирующая стадия с запуском 1С MUST использовать адаптер из capability `long-operation-observation` и писать собственный `observation.jsonl`. Верхний уровень MUST писать `<run-root>/observation.jsonl` и `progress.txt` с текущей стадией. Контрольные точки в журнале регистрации MUST содержать только `runId`, операцию, этап и результат.

#### Scenario: Стадия загрузки правил зависла

- **WHEN** прикладной прогресс стадии `load` не меняется дольше `runtimeStageTimeoutSeconds`
- **THEN** стадия остановлена, `result.json` имеет статус `failed`, а `observation.jsonl` стадии содержит terminal `failed`

### Requirement: Регламент правил задаёт правила написания и проверки алгоритмов КД

Регламент `docs/agent/kd21-rules-workbench-runbook.md` MUST содержать:

- **Параметры объекта.** `ПараметрыОбъекта` в алгоритмах КД 2.1 — индексируемый контейнер, а не `Структура`; обязательный ключ читается как `ПараметрыОбъекта["Имя"]`, необязательный — тем же доступом внутри `Попытка/Исключение`.
- **Режим совместимости.** Алгоритмы для конфигурации-источника и конфигурации-приёмника пишутся с учётом режима совместимости каждой из них.
- **Проверка исполнением.** Алгоритм подтверждается исполнением сценария на целевой платформе, а не текстовой проверкой.
- **Число прогонов.** Один принимаемый прогон достаточен по умолчанию; второе поколение запускается только по прямому запросу.
- **Хранение доказательств.** Доказательства хранятся вне Git.

#### Scenario: Разработчик пишет алгоритм с необязательным параметром

- **WHEN** разработчик следует регламенту для чтения необязательного параметра объекта
- **THEN** алгоритм использует индексный доступ внутри `Попытка/Исключение` и не вызывает `ПараметрыОбъекта.Свойство`

### Requirement: Прикладные стадии подключаются как расширения сценария

Исполнитель MUST позволять проекту объявлять в сценарии дополнительные узлы с именем, зависимостями, входами, выходами и режимом повтора (`probe-and-reuse`, `idempotent-retry`, `fresh-generation-required`). Исполнитель MUST отказывать в запуске узла, пока не готовы его прямые зависимости. Отсутствующие изменяющие зависимости MUST NOT выполняться автоматически.

#### Scenario: Запуск узла без готовой зависимости

- **WHEN** запускается `run <узел>`, а его зависимость `load` ещё не выполнена в этом `run-root`
- **THEN** исполнитель завершается ошибкой с именем неготовой зависимости и не запускает `load` сам
