## Why

Прикладной проект `tn-bp30-sdd` (создан из шаблона, overlay `v0.3.36`) за время работы накопил инструменты, навыки и регламенты, которые нужны любому 1С-проекту на этом шаблоне:

- наблюдение длительных операций и технологический журнал;
- штатный запуск клиента 1С агентом для визуальной проверки;
- единая проверка BSL в точном контуре платформы и режима совместимости;
- CLI метаданных, который заменил импортированные редакторы `meta-*`, `form-*` и `cfe-borrow`, конвертация обычных форм, работа с контейнерами `v8unpack`;
- локальный доступ к стандартам `v8std`;
- регламенты удалённой работы на серверах заказчика через VDI;
- выпуск правил обмена КД 2.01 компилятором на Python без 1С и их проверка на расходуемых базах для миграции данных между конфигурациями.

Сейчас всё это живёт только в одном проекте. В шаблон это попадает двумя путями, и оба плохие:

- На 2026-10-08 (коммит проекта `46c814b51`) 181 template-managed файл проекта отличается от `v0.3.36`. Ещё 70 путей проект убрал из своего `template-managed-paths.txt`, когда вывел импортированные редакторы метаданных. Следующий `make template-update` перезапишет правки и вернёт удалённые навыки.
- Новые проекты повторяют ту же работу заново.

Нужно перенести переносимую часть в шаблон, обезличить её и отделить обязательный базовый инструментарий от необязательных модулей. После релиза шаблона проект сможет выполнить обновление без потери своих доработок.

## What Changes

**Базовый инструментарий (поставляется всем создаваемым проектам):**

- Добавить навык `1c-observe-run` и общий адаптер наблюдения. В проекте адаптер встроен в `scripts/lib/capability.sh` (`run_observed_command`) и, для Windows, в `scripts/python/runtime.py` (`observe-command`). В шаблоне его нужно разложить по модулям `runtime_*`. Адаптер даёт:
  - `observation.jsonl` со schema v1: `started`, heartbeat, ровно один terminal `completed|failed`;
  - `progress.txt` и terminal-секцию `summary.json`;
  - ограниченный по времени и событиям технологический журнал через operation cursor точного запуска (`scripts/diag/technological-log.sh`);
  - новое поведение (решение Р7): остановку процессной группы, если прикладной прогресс не меняется дольше порога, который передала обёртка. В проекте такая остановка есть только в исполнителе КД (`stall_timeout` в `kd_cycle_common.run`).
- Подключить этот адаптер ко всем запускам клиента и Designer в штатных обёртках на Linux и Windows: `direct-platform.sh`, `db-run`, `run-client`, EPF/ERF build/dump, операции с временными файловыми ИБ.
- Добавить навык `1c-run-client` и обёртки `scripts/platform/run-client.sh|.ps1` (`run_client.py`). Обёртка открывает базу runtime-профиля в отдельном Xpra-сеансе, делает снимок экрана, нажимает клавиши и закрывает клиент. Пароль берётся из профиля (решение Р8).
- Добавить единую проверку BSL:
  - навык `1c-check-bsl` и сценарий `scripts/platform/check-cf-modules.sh` — выборочная платформенная компиляция модулей в указанной ИБ;
  - маршрутизация `bsl-analyzer` `check` с точным подключением (`resolve-bsl-analyzer-connections.py`, `external_bsl_check.py`);
  - правило: синтаксис и доступность функций проверяются для каждой затронутой конфигурации на её версии платформы и в её режиме совместимости.
- Перенести в шаблон:
  - CLI метаданных `scripts/python/metadata*.py` и навыки `metadata-use`, `metadata-cli-development` — чтение и изменение XML-выгрузки, включая элементы форм и табличные макеты, через модель объектов, без ручного редактирования XML;
  - конвертацию обычных форм `ordinary_form_conversion.py`, навыки `ordinary-form-workflow`, `prepare-external-artifact`, `cfe-form-workflow` и регламент `docs/agent/ordinary-form-conversion-runbook.md`;
  - работу с контейнерами `v8unpack` (`v8unpack_container.py`, `v8unpack_erf_form.py`, навык `v8unpack`);
  - локальный кеш и поиск стандартов `v8std` (`v8std.py`, `scripts/tools/v8std-fetch`, `v8std-search`), кеш хранится вне Git;
  - единый поисковый регламент `docs/agent/repository-search-runbook.md` и регламент `docs/agent/bsl-analyzer-workspace-runbook.md`;
  - навыки `1c-rac-operations`, `1c-linux-crash-diagnostics`, `legacy-customization-port` в обезличенном виде.
- Вывести из импортированного пакета `cc-1c-skills` навыки `meta-info`, `meta-compile`, `meta-edit`, `meta-remove`, `meta-validate`, `form-info`, `form-add`, `form-compile`, `form-edit`, `form-remove`, `form-validate`, `cfe-borrow`. Их заменяет CLI `metadata`, `sync-imported-skills` их пропускает (решение Р6). Навык `form-patterns` остаётся.
- Добавить в `qa.py` / `check-skill-bindings` проверку того, что пути репозитория, упомянутые в `SKILL.md`, существуют.
- Добавить gate статической типизации Python (basedpyright):
  - `pyrightconfig.json`, `basedpyright-baseline.json`, `basedpyright-baseline-count.json`, `scripts/python/type_checking.py`, `scripts/qa/type-check.sh|.ps1`, `scripts/qa/type-check-update-baseline.sh|.ps1` и smoke-контракт. Проект уже добавил эти пути в свой `template-managed-paths.txt`, в шаблоне их нет;
  - в шаблоне нет `pyproject.toml` и `uv.lock`: их нужно создать с dev-зависимостью basedpyright;
  - `requirements-dev.txt` поставлять как производный export из `uv.lock`.
- Перенести проверенные правки проекта в template-managed сценарии, после ревью каждого файла и без проектных имён:
  - `check-agent-docs.sh`, `qa.py`, `export-context.sh`;
  - `runtime*.py` — с учётом разбиения на модули `runtime_*` в шаблоне;
  - `capability.sh`, `imported_skills.py`, `direct-platform.sh`, `context.py`, `cli.py`;
  - `manage-cfe.sh`, `designer-diagnostics.sh`, `create-ib.sh`, `check-cfe-config.sh`, `update-db.sh`;
  - `run-yaxunit-warm-service.sh`, `configure-cfe-runtime-flags.sh`;
  - прочие файлы из списка расхождений.

**Необязательный модуль «Операции на внешней площадке заказчика» (`customer-site-operations`):**

- Поставлять обезличенную заготовку. В проект она материализуется только явной командой инициализации.
- Состав заготовки:
  - регламент площадки: разрешённые границы, запрет секретов в командах, машинная сверка SHA-256, одна ASCII-строка до 4096 символов, запрет `exit`/`logout`/`exec`, раздельные read-only и изменяющие команды, Enter только после проверки снимка экрана;
  - шаблоны инвентаря и профилей без IP, CIDR, UUID и имён серверов;
  - инструменты оператора:
    - запуск VDI-клиента в изолированном Xpra;
    - ввод команды с проверкой набранной строки;
    - передача файла фрагментами gzip+base64 с проверкой SHA-256 до `sudo install`;
    - keepalive мыши;
  - серверные обёртки только на стандартной библиотеке Python для системного Python площадки:
    - `trac`/`tnl-rac` → `site-rac`, включая включение и отключение регламентных заданий базы (`jobs-on`/`jobs-off`);
    - `tnl-ibcmd` → `site-ibcmd`;
    - golden, архив и восстановление DT, создание согласованной копии базы из DT и удаление неудачной копии;
    - управление технологическим журналом;
    - подготовка офлайн-лицензирования;
  - навыки `site-vdi-xpra` (обобщение `tnl-citrix-xpra`), `rdp-bash-payload`, `1c-password-recovery` (отдельной опцией модуля, см. «Принятые решения», п. 2).

**Необязательный модуль «Правила миграции данных на КД 2.01» (`kd21-migration-rules-workbench`):**

- Поставлять ядро компилятора правил `kd_xml_compiler` (решение Р5). Ядро строит файлы выпуска правил формата КД 2.01 из `scenario.json` и метаданных конфигураций без запуска 1С. Состав ядра:
  - нейтральная модель метаданных и модель правил;
  - сериализатор КД 2.01 с детерминированным порядком элементов и правил регистрации;
  - адаптер XML структуры метаданных и обработка выгрузки структуры из базы (`metadata-exporter`).
  Ядро не импортирует проектные модули. Наложение изменений CFE, сценарии конкретных конфигураций и шаблоны текстов обработчиков остаются в проекте.
- Поставлять обобщённый исполнитель рабочего контура правил со следующими свойствами:
  - профиль с двумя расходуемыми базами: база-источник и база-приёмник;
  - неизменяемые эталонные базы, из которых восстанавливаются расходуемые;
  - сценарий `scenario.json` с версиями конфигураций, пространством имён и UUID конвертации, SHA-256 закреплённых XML структуры метаданных;
  - стадии `doctor → reset → build → load → run → verify`, где `build` вызывает компилятор, а `load` загружает правила в обе расходуемые базы штатной обработкой и тем самым проверяет, что платформа их принимает;
  - блокировка профиля, одноразовый `run-root`, `state.json`, итоговый `result.json`;
  - статусы `in-progress|failed|workbench-run-passed|workbench-ready`, а для отдельной сборки выпуска без баз (`run build-rules`) — `rules-built`;
  - манифест выпуска правил с SHA-256 файлов XML и ZIP;
  - неизменность баз-источников фиксируется в `source-before.json` и `source-after.json`.
- Поставлять регламент разработки правил:
  - один принимаемый прогон по умолчанию, второе поколение для сравнения — только по прямому запросу;
  - учёт режима совместимости каждой конфигурации в текстах обработчиков;
  - обязательная проверка исполнением на платформе;
  - запрет текстовых «проверок» BSL;
  - изменение компилятора подтверждается сравнением выпуска с закреплённым эталоном;
  - хранение доказательств вне Git.
- Поставлять навык `1c-prepare-manual-migration-bases` в обобщённом виде и заготовку раздела `## Влияние на миграцию` для proposal прикладных changes.
- Не переносить прикладные правила обмена, сценарии волн НСИ и документов, матрицы счетов, обезличку и паспорта эталонов проекта.

**Не входит в change:**

- прикладной код и метаданные БП 2.0/3.0, расширение `ТНЛ_АдаптацияБП30`;
- сведения о площадке заказчика: имена серверов, адреса, учётные записи, итоги по базам;
- исследовательские деревья сравнения конфигураций;
- сборка поставки `1c-delivery-build`;
- проектный слой компилятора КД: наложение CFE, сценарии БП 2.0 → БП 3.0, перенос обработчиков в общие модули конфигураций, параллельный обмен и сверка;
- запуск клиента через Power Automate Desktop PiP Child session (change проекта `add-windows-pip-1c-techlog` не завершён);
- правила конкретного OpenSpec-проекта о миграционных draft changes (кроме обобщённой заготовки раздела).

## Capabilities

### New Capabilities

- `long-operation-observation`: единый контракт наблюдения за запусками клиента, Designer и длительными операциями с ИБ на Linux и Windows, включая технологический журнал.
- `onec-development-toolkit`: запуск клиента для визуальной проверки, проверка BSL в точном контуре, CLI метаданных, конвертация обычных форм и внешних обработок, `v8unpack`, стандарты `v8std`, поисковый регламент.
- `customer-site-operations`: необязательный обезличенный модуль удалённой работы на серверах заказчика через VDI, Xpra и серверные обёртки на стандартной библиотеке.
- `kd21-migration-rules-workbench`: необязательный модуль сборки правил обмена КД 2.01 компилятором и их проверки на расходуемых базах.

### Modified Capabilities

- `project-scoped-skills`: новые навыки базового набора и необязательных модулей; вывод импортированных редакторов метаданных; проверка существования путей, упомянутых в навыках.
- `template-overlay-delivery`: заготовки необязательных модулей обновляются overlay, а материализованные каталоги остаются project-owned; перенос правок проекта в шаблон выполняется до `template-update` проекта.
- `template-ci-contours`: gate статической типизации Python и smoke-контракты новых инструментов в лёгком контуре без 1С.

## Принятые решения

Пользователь 2026-09-27 согласился с рекомендациями по пунктам 1–4, 2026-10-08 — по пунктам 5–8. Подробности и последствия — в `design.md`, раздел «Принятые решения».

1. Необязательные модули включаются командой `make optional-module-init MODULE=<имя>`, а не вопросом Copier.
2. Обёртка восстановления доступа через `v8users` поставляется отдельной опцией модуля площадки с предупреждением и обязательной резервной копией.
3. Исполнитель КД в шаблоне — минимальное ядро; прикладные стадии остаются расширениями проекта.
4. Базовый инструментарий выпускается отдельной версией шаблона до необязательных модулей.
5. Модуль КД строится вокруг ядра компилятора `kd_xml_compiler` и двух расходуемых баз; база КД 2.1 и `КД21Исполнитель.epf` не поставляются.
6. Импортированные `meta-*`, `form-*` (кроме `form-patterns`) и `cfe-borrow` выводятся из шаблона в пользу CLI `metadata`.
7. Остановка при неизменном прогрессе — новое поведение общего адаптера; порог задаёт обёртка, по умолчанию остановка выключена.
8. В базовый набор входят `1c-run-client` и Windows-наблюдение `observe-command`; PiP Child session не входит.
