## Context

Шаблон уже поставляет BDD, тёплый сервис Vanessa Automation и восстановление золотой базы, но не хранит переносимый протокол длительного прогона. В Delans этот пробел закрыт файлами кампании и очереди, однако состояние, команды и история там привязаны к конкретному проекту.

## Goals / Non-Goals

**Goals:**

- перенести формат кампании и возможность продолжать её между сеансами;
- извлечь из Delans только переиспользуемый 1С-слой тестового контура;
- отделить версионируемые исходники контура от локальных бинарных зависимостей;
- дать человеку и агенту одну версионируемую команду вместо ручного редактирования JSONL;
- безопасно поставлять инструмент при первичном создании и обновлении проекта;
- проверять статические и файловые контракты без запуска 1С, а совместимость очищенных расширений подтверждать отдельным provisioned-runtime gate.

**Non-Goals:**

- перенос feature-файлов, профилей, данных, `DelansCommon` целиком, прикладных тестов Delans и истории запусков;
- новый исполнитель тестов или замена существующих BDD и golden entrypoint-ов;
- параллельный планировщик, блокировки между машинами или база данных состояния.

## Decisions

1. Сохранить проверенный файловый формат Delans: `campaign.json`, `queue.jsonl` и короткий указатель активной кампании. Альтернатива с единой базой данных сложнее и не нужна для последовательной работы одного агента.
2. Реализовать команды `init`, `use`, `next`, `set` и `status` в `scripts/python/testing_campaign.py`, подключить их к существующему `scripts/python/cli.py` и дать тонкие `scripts/test/testing-campaign.sh` и `scripts/test/testing-campaign.ps1`. `use <id>` проверяет существующую кампанию и атомарно заменяет указатель активной кампании. Так Linux и Windows получают один контракт, а JSON и атомарная замена реализуются стандартной библиотекой Python без нового парсера или зависимости.
3. `campaign.json` имеет `schemaVersion: 1`, `id`, `createdAt` и объект `entrypoints` с ровно тремя непустыми строками `prepareGolden`, `startWarmService` и `runJob`. `queue.jsonl` содержит по одному объекту на строку с обязательными `id`, `kind`, `status`, `selector` и необязательным `resultDir`. `id` кампании и задания удовлетворяет `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`, идентификаторы заданий уникальны. Для `vanessa-bdd` selector содержит только непустой project-relative `featurePath`; для `yaxunit` — только объект `filters` хотя бы с одним непустым массивом `extensions`, `modules`, `tests`, `tags` или `paths`. Неизвестные поля отклоняются. Абсолютные пути и сегмент `..` запрещены в `featurePath` и `resultDir`.
4. Не исполнять произвольные команды из кампании внутри управляющего сценария. Сценарий только возвращает выбранное задание и меняет состояние; существующие тестовые entrypoint-ы остаются единственным исполнительным слоем.
5. При bootstrap поставлять документацию, управляющие команды, заготовки и пустой каталог `analysis/testing/campaigns/.gitkeep`. `active-campaign.txt`, кампании, очереди и результаты создаются только командой `init`, поэтому новый проект не получает ложное активное состояние.
6. Состояние `analysis/testing/` является проектным и не должно перезаписываться overlay-обновлением. Версионируемые сценарий, документация и smoke-проверка обновляются обычным путём шаблона.
7. Один smoke-сценарий вызывает обе тонкие обёртки там, где среда это позволяет, и покрывает контракт на временном каталоге; Linux baseline обязательно проверяет Python/Bash путь, а существующий PowerShell fixture-контур проверяет маршрутизацию `.ps1`. Отдельный тестовый каркас не вводится.
8. Переносимая часть Vanessa строится из `VATestContour`: код не содержит ссылок на Delans и реализует загрузку Vanessa Automation Single, запуск по параметру, файловый протокол `RUN`/`STOP`, готовность и завершение прогона. Из заготовки безусловно удаляется заимствованный `ОбщегоНазначенияКлиентПереопределяемый` с UUID базовой конфигурации. Источниками для поведенческого сравнения служат текущие файлы `DC_BDDWarmServiceGlobal` SHA-256 `4ff1fc4e73c22f8df210911986598fe58c2dc92b7314b880bf2468ceeca3bb09` и `DC_BDDWarmServiceServerCall` SHA-256 `100f170cdceda532312952d11dcc72bab0af5ceaf120e59fbab1f794467a2fa2`; из них переносятся только отсутствующие в `VATestContour` инфраструктурные исправления. `DelansCommon` целиком не переносится.
9. `DelansYAxUnitTests` не переносится как готовое расширение: его тест формы `ЗащитаПерсональныхДанных` и имена Delans прикладные. Из него формируется обезличенный каркас `ProjectYAxUnitTests` с подсистемой подключения тестовых модулей и совместимым с изолированной проверкой расширения способом регистрации тестов. После копирования каркас принадлежит целевому проекту и не перезаписывается overlay-обновлением.
10. Версионируемые заготовки `VATestContour` и `ProjectYAxUnitTests` хранятся под `automation/testing/templates/`. Исходными деревьями для извлечения служат чистые Git trees Delans: `VATestContour`=`3a289ff004088f3dece757ea41cc9081ac45d813`, `DelansYAxUnitTests`=`ca01a015dcb5a310d6b0c602fe41051bc0c7d23c`, YAxUnit=`9df32496af0985735968594c126a7e4bffb54e18`, VAExtension=`2d8b3b72df05c0282403f5b0c34d2235e2369462`. Закреплённые source-only деревья YAxUnit 25.12 (Apache-2.0; официальный CFE SHA-256 `805a2277c997a3c24be0b0d080696479e91e4a15ed7e27aaf3991a7346522d70`) и VAExtension 1.29 (BSD-3-Clause; CFE SHA-256 `fc557bb23371a37dbe22a7a7a83e28f6db75b57f87e8802028cf1f90c4e00605`) хранятся под `automation/testing/vendor/` вместе с текстами лицензий. Официальные CFE используются только как provenance-входы и не устанавливаются этим change: существующий runtime синхронизирует XML-исходники через `load-cfe`. `UPSTREAM.json` фиксирует официальный repository/release URL, tag, asset и SHA-256, исходный Delans Git tree id и детерминированный SHA-256 отсортированного списка `relative-path + NUL + file-hash`; это доказывает точный источник переносимого XML-дерева без зависимости от грязного состояния соседнего репозитория. Команда `init-test-tooling --project-tests-name <name>` копирует четыре дерева в `src/cfe`, пересоздаёт UUID только у project-owned заготовки тестов и отказывается изменять любой существующий целевой каталог. После копирования все четыре каталога под `src/cfe` являются project-owned; обновление наложения меняет только исходные заготовки и vendor-source, но не применяет их повторно автоматически.
11. Единственный устанавливаемый бинарник этого change — `vanessa-automation-single.epf` из выпуска Vanessa Automation `1.2.043.28`, извлекаемый из `vanessa-automation-single.1.2.043.28.zip`. Ожидаемый SHA-256 ZIP — `cd0a017a8af69328f471f628ac1367a0e5148f790df9c28c318348b30f08f32a`, итогового EPF — `97cf472753c44f3b391062ad918f01a6e0a5932f230570c3102ab22e44df7a48`. `install-test-tooling [--archive <local-zip>]` загружает либо читает локальный архив во временном каталоге, до распаковки проверяет ZIP SHA-256, отклоняет абсолютные пути, `..`, ссылки и более одного ожидаемого EPF, затем проверяет EPF SHA-256 и атомарно публикует его в `.artifacts/testing/vanessa/1.2.043.28/vanessa-automation-single.epf`. Уже проверенный файл с тем же хешем переиспользуется; несовпадение или ошибка сети не меняют ранее установленный файл. URL выпуска, имя asset, версия, оба SHA-256 и лицензия BSD-3-Clause фиксируются в `automation/testing/dependencies.json`.
12. `init-test-tooling` и `install-test-tooling` являются разными операциями: первая не требует сети и создаёт отслеживаемые project-owned исходники, вторая изменяет только игнорируемый локальный кэш. Ни одна из них не запускается автоматически при bootstrap или overlay update. Runtime-профиль продолжает использовать существующее поле `capabilities.bddWarmService.vanessaSinglePath`, которому документация показывает repo-relative путь установленного EPF; схема runtime-профиля не меняется.
13. Команда `init` принимает `--id`, `--queue <jsonl>` и `--entrypoints <json>`, полностью проверяет оба входных файла во временном каталоге и только затем создаёт каталог кампании и атомарно заменяет `active-campaign.txt`; при ошибке временный и частично опубликованный каталог удаляются. Повторный `init` с существующим id завершается без изменений. `use` не меняет кампанию и только атомарно выбирает существующую корректную кампанию. `next` и `status` выводят один JSON-объект в stdout; отсутствие исполняемого задания является успешным результатом с `job: null`.
14. `set` допускает переходы `pending → running|blocked|skipped_by_policy`, `running → done|failed_retry|blocked` и `failed_retry → running|blocked|skipped_by_policy`; конечные `done`, `blocked`, `skipped_by_policy` неизменяемы. Для `done` обязателен project-relative `resultDir`; для остальных состояний он запрещён. Запись выполняется через временный файл в каталоге очереди и `os.replace`. Контракт рассчитан на одного писателя; межпроцессная и межмашинная блокировка остаётся вне scope.
15. Откат исходников выполняется обычным Git revert project-owned каталогов. Откат бинарника выполняется возвратом значения `vanessaSinglePath` на ранее сохранённый versioned-каталог `.artifacts/testing/vanessa/<version>/`; установщик не удаляет другие версии. Обновление upstream-source и версии EPF требует отдельного change с обновлением provenance, хешей и fixture/provisioned-runtime проверок.
16. Все операции с состоянием отказываются работать через символические ссылки в `analysis/testing`, `active-campaign.txt`, каталоге кампании или `queue.jsonl` и после разрешения пути проверяют принадлежность корню репозитория. Entry-point строки являются только отображаемыми данными: инструмент не выполняет их, не подставляет переменные и документация запрещает помещать туда секреты, предписывая использовать существующую env-indirection runtime-профилей.
17. `next` возвращает `{"campaignId": "...", "job": <object|null>}`, `status` — `campaignId`, `schemaVersion` и счётчики по каждому допустимому состоянию. Неизвестная schemaVersion, отсутствующий/повреждённый active pointer, неизвестные поля и некорректная JSONL-строка приводят к non-zero без изменения файлов. `createdAt` записывается в UTC RFC 3339. Миграция будущих версий не входит в этот change: новый schemaVersion потребует отдельного явного мигратора, а v1 остаётся fail-closed.
18. Все операции очереди линейны по числу строк и переписывают один JSONL-файл целиком. Это принятый предел последовательной кампании одного агента; индекс или база данных добавляются только при измеренной проблеме на реальных очередях.

19. Производный снимок VAExtension сохраняет исходные UUID и отличается от upstream только патчем совместимости: недоступные операции исключены из компиляции WebClient, а две команды форм без обработчиков удалены. `UPSTREAM.json` хранит хеш исходного upstream-дерева, хеш производного дерева и перечень патчей.

## Risks / Trade-offs

- Одновременная запись двумя процессами может привести к последней победившей записи → формат предназначен для последовательной кампании; межпроцессную блокировку добавлять только при реальной потребности в параллельном диспетчере.
- Проект может хранить неверные команды запуска → инструмент не исполняет их и документация требует проверять команды через существующие entrypoint-ы.
- Overlay может затронуть проектное состояние → манифест и smoke-проверка должны подтверждать, что `analysis/testing/active-campaign.txt` и `campaigns/*` не являются обновляемыми skeleton-файлами.
- Заимствованный объект `VATestContour` может привязать расширение к UUID конкретной конфигурации → переносимый вариант не содержит таких объектов, а smoke-проверка запрещает известный UUID прототипа.
- Источник внешнего бинарника может исчезнуть или измениться → установка требует закреплённой версии и совпадения SHA-256 и завершается до изменения рабочего контура при несовпадении.
- Закреплённые YAxUnit/VAExtension могут отстать от upstream → обновление выполняется только отдельным проверяемым change; скрытого обновления на latest нет.
- Статическая проверка XML не доказывает переносимость между конфигурациями → перед объявлением контура готовым обязательны `check-cfe-config`, `check-cfe-applicability`, загрузка и минимальные реальные запуски в Delans на target `delans_ut_26_bdd` и `delans_unf_bdd`.
- Source-only снимки YAxUnit и VAExtension увеличивают каждый создаваемый репозиторий примерно на 11 МБ → это осознанная цена автономной и воспроизводимой инициализации; бинарный EPF размером около 24 МБ остаётся вне Git.
