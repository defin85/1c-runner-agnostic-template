# `site-v8users-recovery`: восстановление доступа к базе 1С на PostgreSQL

> **Недокументированный метод.** Обёртка напрямую меняет служебные таблицы 1С
> (`v8users` и запись `users.usr` в `params`). Это не API платформы: поведение
> может измениться в любой версии 1С или PostgreSQL. Успех на одной базе не
> доказывает применимость к другой.

## Проверенные версии

Метод проверен в исходном проекте только на платформе **8.3.27** и
**PostgreSQL 16**: вход в Конфигуратор без пароля, возврат исходных
пользователей, штатная смена пароля и новый вход. Другие версии не проверялись.

Перед первым применением в проекте проверьте метод на копии базы и запишите
результат сюда:

## Когда применять

- Только при потерянном доступе, если сохранённые реквизиты не работают
  (сначала `site-rac info`), и только с разрешения на конкретную базу и
  пользователя.
- Опция выключена по умолчанию. Включение — в профиле `site.json`:

  ```json
  "v8users_recovery": {"enabled": true, "databases": ["app_main_copy"]}
  ```

  База должна быть ещё и в `infobases`. Без этого любая команда отказывает до
  обращения к СУБД.
- В профиле нужен `pg_bin` — каталог клиентских утилит PostgreSQL.

## Порядок

Строго `backup → hide → вход в Конфигуратор → restore → verify`. Каждая команда —
отдельный запуск на сервере СУБД от владельца приватного рабочего каталога с
доступом к PostgreSQL через peer или защищённый `.pgpass` (пароль в аргументы не
передаётся).

```bash
W=/var/lib/site-recovery/app_main_copy-RUN
python3 /opt/site-ops/site-v8users-recovery status --database app_main_copy --host /run/postgresql --work "$W"
python3 /opt/site-ops/site-v8users-recovery backup --database app_main_copy --host /run/postgresql --work "$W" --confirm app_main_copy
```

1. `status` — только чтение: OID таблиц, число записей `users.usr`, активные
   клиенты.
2. `backup` создаёт новый каталог `--work` (0700) и резервную копию:
   - по умолчанию — полный custom dump базы (`BACKUP_READABLE`: архив читается,
     пробное восстановление не выполнялось);
   - `--scope tables` — для крупных баз: только схема, `v8users` и запись
     `users.usr` с проверкой копии по живым строкам (`BACKUP_VERIFIED`).
3. `hide` отказывает без `state.json` проверенной резервной копии в `--work`.
   В одной транзакции проверяет, что данные не изменились с момента копии,
   переименовывает `v8users` в `v8users_site_recovery`, запись `users.usr` — в
   `users.usr_site_recovery` и создаёт пустую `v8users` по образцу исходной.
4. Откройте Конфигуратор этой базы без имени и пароля (для Windows-клиента —
   с отключённой аутентификацией ОС `/WA-`) и **не закрывайте его**. Пока
   список скрыт, не создавайте пользователей и не сохраняйте пустой список.
5. `restore` при открытом Конфигураторе возвращает исходную таблицу и запись.
   Пустая временная таблица и временная запись сохраняются под именами
   `v8users_site_created` и `users.usr_site_created`. Если во временной таблице
   появились пользователи, `restore` останавливается и ничего не удаляет.
6. В Конфигураторе заново откройте список пользователей и смените пароль
   выбранного пользователя штатно. Новый пароль вводите скрыто или берите из
   согласованного защищённого источника.
7. `verify` сверяет возвращённые данные с отпечатком до `hide`
   (`BACKUP_RESTORE_VERIFIED`). Затем проверьте новый вход.

## Прерывание

- Сначала `status` и `state.json` в `--work`. Не повторяйте `hide`.
- `restore` разрешён и при этапе `backed-up`, если `hide` успел выполниться,
  а запись состояния прервалась: проверяется OID сохранённой таблицы.
- Если `restore` отказал — сохраните объекты и резервную копию и разберите
  причину. Не используйте `DROP`, `CASCADE` или ручную чистку `params`.
- Резервную копию и таблицы `*_site_created` в этом процессе не удаляйте.
  Повторный опыт — только с новым `--work`.
- Не выводите содержимое `v8users`, `params` и паролей: для диагностики
  достаточно счётчиков и кодов результата.
