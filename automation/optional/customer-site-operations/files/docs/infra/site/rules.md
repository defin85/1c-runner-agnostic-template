# Регламент работы на площадке

Правила для агента и оператора. Состав серверов, версии и пути — в
[inventory.md](inventory.md). Снимки и журналы считайте навигацией: перед
изменением перепроверяйте относящиеся к нему факты на живой системе.

## Доступ

- VDI-клиент заказчика запускайте на хосте оператора в отдельном фоновом Xpra
  по навыку `site-vdi-xpra`. Xpra работает без буфера обмена и передачи файлов;
  окно просмотра открывайте только по просьбе пользователя.
- Уже запущенный сеанс сначала осмотрите по снимку экрана и используйте без
  перезапуска. Остановка Xpra может оборвать удалённую операцию.
- Разрешение работать в сеансе (вводить команды, нажимать Enter после сверки)
  не расширяет круг разрешённых изменений серверов и баз. Каждое изменение
  согласуйте отдельно, повторно не спрашивайте уже полученное разрешение.
- Ручной режим через RDP-shell (оператор вставляет команду сам) описан в
  навыке `site-rdp-bash-payload`.

## Ввод команд в удалённый терминал

- Команда — одна непустая строка ASCII длиной до 4096 символов, без переводов
  строк, here-document и продолжений через обратную косую черту.
- Не включайте `exit`, `logout` и заменяющий shell `exec`, в том числе внутри
  `bash -c`: при повреждении кавычек они закрывают удалённый shell. Код результата
  сохраняйте в переменную и оставляйте shell открытым.
- Не включайте кириллицу даже в regex и строковые литералы: эмуляция клавиатуры
  её теряет. Перед вводом убедитесь, что в удалённом сеансе английская раскладка:
  при другой раскладке искажаются `/`, `.`, `"` и `|`.
- Порядок: `site-operator type` набирает строку без Enter → снимок экрана →
  `site-operator verify` сравнивает набранную строку с исходной → только после
  `verify_match=1` команда `site-operator enter` отправляет Enter. При расхождении
  очистите строку в терминале (`Ctrl+U`) и наберите команду заново, не
  исправляйте длинную строку на месте.
- Read-only диагностику и изменение не объединяйте в одной команде. Каждая
  команда — отдельный шаг с отдельной проверкой результата.
- Составную root-команду собирайте через `site-operator payload`: он проверяет
  payload через `bash -n` и формирует `sudo -n /bin/bash -c '<payload>'`.
  `set -e`, `set -u` и `set -o pipefail` допустимы только внутри `bash -c`, не
  в интерактивном shell.
- Файлы передавайте только `site-operator transfer`: фрагменты gzip+base64 по
  240 символов во временный файл, затем машинная сверка SHA-256 и установка
  `sudo -n install` только при совпадении. Код последней команды конвейера не
  считайте успехом переноса — нужна строка `sha256_match=1`.
- Контрольные суммы и длинные идентификаторы не переписывайте со скриншота.
  Сверяйте их машинно на удалённом узле и фиксируйте значение только после
  явного `match`.
- Вывод, ограниченный `head`, не считайте полным перечнем.

## Порядок работы

- Начинайте с read-only проверок. Production, сеть, firewall, службы, лицензии,
  базы и снимки меняйте только в явно разрешённых границах.
- Наличие файла проверяйте `test -e`, право исполнения — отдельно `test -x`:
  отрицательный `test -x` не доказывает отсутствие файла.
- Перед `sudo` проверяйте разрешение именно этой операции через `sudo -l`.
  Успешный `sudo -v` подтверждает пароль, но не право запуска.
- Доступность CLI проверяйте отдельным `command -v` с учётом кода возврата.
- Путь `rac` берите из профиля площадки (`platform.rac`), а не выводите из
  версии активного systemd-unit. Справка вызывается как `rac help MODE 2>&1`.
- Опции локального `rac` не переносите на удалённый сервер другой версии:
  проверяйте контракт установленного там `rac`.
- Перед `runuser` переходите в каталог, доступный целевому пользователю
  (например, `/`).
- Технологический журнал 1С не построчный CSV: события бывают многострочными.
  Наружу выводите только агрегаты или поля из заранее заданного списка.
- Фильтрацию потенциально секретного вывода стройте fail-closed: печатайте
  только константы и счётчики, не пропускайте сырые строки через `grep`.
- Необязательную диагностическую утилиту сначала проверьте на наличие; не
  устанавливайте пакеты на сервере заказчика ради диагностики.
- Контур может быть офлайн: пакеты берите только из проверенного локального
  комплекта, не подключайте внешние репозитории на серверах.

## Безопасность и секреты

- Не помещайте в Git, документацию, журналы и вывод агента пароли, PIN-коды,
  регистрационные данные, закрытые ключи, содержимое `.lic`, файлы запросов и
  ответов лицензирования, содержимое файлов подключения VDI.
- Пароли обёрток хранятся в отдельных файлах `root:root 0600`; профиль площадки
  содержит только пути к ним. Обёртки не выводят argv инструментов и сырой вывод
  при ошибке, журнал ошибки маскирует пароли.
- Снимки экрана могут содержать данные заказчика: храните их только в приватном
  runtime-каталоге оператора, не добавляйте в репозиторий.
- Реальные сведения о площадке (адреса, имена серверов и баз, учётные записи,
  итоги операций) держите только в project-owned файлах проекта, а не в шаблоне.

## 1С, лицензия и восстановление

- Наличие `.lic`, активного кластера или регистрации базы не доказывает
  исправность серверной лицензии. Критерий — успешная серверная операция и
  подключение клиента без ошибки лицензирования.
- Перед restore или create проверяйте точную цель, отсутствие конфликта имён,
  доступность СУБД, версии инструментов и точку возврата. Не загружайте DT
  поверх частично созданной или неизвестной базы.
- Пароль СУБД вводите интерактивно или берите из защищённого файла; после
  операции закрывайте административный сеанс.

## Проверка изменений

- Для каждого изменения оставляйте минимальную воспроизводимую проверку
  затронутого слоя; синтаксическая проверка не заменяет live-приёмку.
- Не делайте commit, push и изменения production без отдельного явного запроса.
