# Рабочий контур правил КД 2.01

Регламент описывает сборку правил обмена формата КД 2.01 компилятором на Python и их проверку платформой на двух расходуемых базах через `scripts/migration/kd-rules-cycle` (Windows: `scripts/migration/kd-rules-cycle.ps1`).

Документ создан командой `make optional-module-init MODULE=kd21-migration` и принадлежит проекту: дописывайте в него проектные правила.

## Назначение и границы

- Компилятор `scripts/migration/kd_xml_compiler/` собирает выпуск без 1С: пять XML, три ZIP и `manifest.json`. База КД 2.1, сервер 1С, пароли ИБ и СУБД для сборки не нужны.
- Исполнитель изменяет только две расходуемые базы профиля: базу-источник и базу-приёмник (`workbases`). Эталонные базы (`references`) он не открывает: стадия `reset` восстанавливает расходуемые базы из PostgreSQL golden-снимков эталонов.
- Ядро компилятора не импортирует исполнитель `kd_cycle_*` и проектные модули. Прикладные правила подключаются через `compiler.rulesProvider` сценария, прикладные стадии — через узлы сценария (`nodes`).

## Входы

| Файл | Содержание |
| --- | --- |
| `migration/kd21/profiles/local.json` | Профиль: эталонные и расходуемые базы, лимиты, команды стадий, каталог публикации выпуска. Создаётся из `local.example.json`. |
| `migration/kd21/scenarios/technical-workbench/scenario.json` | Сценарий: версии конфигураций, UUID правил, планы обмена, структуры метаданных с SHA-256. |
| `.../matrix.json` | Пути пяти XML по ролям и состав трёх ZIP. |
| `.../expected.json` | Ожидаемый состав `files` и `archives` манифеста. |

### Профиль

- `references[]` — эталонные базы `source` и `target`: `database` и `snapshot` (golden-снимок `pg_dump`, создаётся `tests/golden/create.sh --profile <профиль эталона> --target <id>`). Необязательный `snapshotSha256` закрепляет снимок.
- `workbases[]` — расходуемые базы `source` и `target`: `database`, `runtimeProfile` (runtime-профиль этой базы) и `target` (значение `target.id` runtime-профиля). Если в runtime-профиле есть `ibcmd.dbmsInfobase.name`, оно обязано совпадать с `database`.
- `expendableDatabases` — список имён баз, которые разрешено восстанавливать. `doctor` и `reset` отказывают, если имя расходуемой базы совпадает с именем эталонной (без учёта регистра) или отсутствует в этом списке.
- `limits.runtimeStageTimeoutSeconds` — порог неизменного прогресса для блокирующих стадий. `limits.stageTimeoutSeconds` — необязательный общий предел до первого сообщения о прогрессе. `minFreeBytes`, `maxReleaseBytes` — проверки места и размера выпуска.
- `requiredEnv` — имена переменных окружения с секретами; `doctor` проверяет их наличие, значения не пишутся в доказательства.
- `commands.reset` — команда восстановления одной расходуемой базы. По умолчанию `bash tests/golden/restore.sh --profile {runtimeProfile} --target {target} --snapshot {snapshot}`; на Windows для неё нужен Git Bash.
- `commands.load` — проектная команда загрузки выпуска в одну расходуемую базу штатной обработкой (в примере профиля — `migration/kd21/bin/load_rules.py`; модуль этот файл не поставляет, его создаёт проект). Обязательна для полного прогона. Если файл скрипта из команды не существует, `doctor` завершается ошибкой `command file not found`.
- `lockDirectory` — каталог блокировок профиля; по умолчанию `<временный каталог>/kd-rules-cycle-locks`, общий для всех рабочих копий машины.

В командах доступны подстановки `{python}` (только первым элементом), `{role}`, `{database}`, `{target}`, `{runtimeProfile}`, `{snapshot}`, `{release}`, `{runRoot}`, `{stageRoot}`, `{resultFile}`, `{progressFile}`, `{runId}`. Неизвестная подстановка — ошибка.

### Структуры метаданных

Структура каждой конфигурации выгружается из живой базы внешней обработкой `migration/kd21/metadata-exporter/`: соберите EPF из исходников, запустите её в базе с параметром запуска `KD21Output=<путь к XML>`. Обработка пишет прогресс в `<путь>.progress.json`, ошибку — в `<путь>.error.txt`. Храните выгрузки вне Git (например, `.artifacts/kd21-structures/<дата>/`) и закрепите в сценарии путь и SHA-256 (`inputs.sourceStructure`, `inputs.sourceStructureSha256` и то же для `target`). Структуры в `scenarios/technical-workbench/structures/` демонстрационные.

## Команды

```bash
./scripts/migration/kd-rules-cycle --profile migration/kd21/profiles/local.json \
  --scenario migration/kd21/scenarios/technical-workbench \
  --run-root /абсолютный/новый/каталог <команда>
```

| Команда | Действие |
| --- | --- |
| `run build-rules` | Собирает выпуск и публикует его в `releasePublishRoot`; статус `rules-built`. Базы не открываются. |
| `all` | Выполняет `doctor`, `reset`, `build`, `load`, `run`, `verify` по порядку; уже пройденные в этом `run-root` стадии пропускает. |
| `doctor` | Проверяет профиль, защиту эталонов, снимки, структуры, матрицу, команды, место; пишет `source-before.json`. |
| `reset` | Восстанавливает обе расходуемые базы из golden-снимков и создаёт новое поколение баз. Требует `doctor`. |
| `build` | Собирает выпуск в `<run-root>/release`. |
| `load` | Загружает выпуск в обе расходуемые базы. Требует `reset` и `build`. |
| `run` | Выполняет все узлы сценария; без узлов проходит сразу. Требует `load`. |
| `run <узел>` | Выполняет один узел, если готовы его прямые зависимости; отсутствующие зависимости сам не запускает. |
| `verify` | Сверяет файлы выпуска с манифестом и `expected.json`, пишет `source-after.json` и сравнивает его с `source-before.json`. Требует `run`. |

`--run-root` — абсолютный каталог вне репозитория. Без материализованного модуля или без профиля команда завершается ошибкой с подсказкой включить модуль.

## Состояние, результат и отказы

- `<run-root>/state.json` (schema 2) хранит отпечаток входов, состояние стадий и узлов, поколения баз и выпуск.
- `<run-root>/result.json` — итог: `status`, `generations`, `stages`, `nodes`, `release` (путь и SHA-256 манифеста), при ошибке `failedStage` и `reason`.
- Если изменился профиль, сценарий, матрица, ожидаемый результат или SHA-256 структуры, команда в том же `run-root` завершается ошибкой `inputs changed; use a new --run-root and reset`.
- После ошибки стадии следующие стадии не выполняются, а `run-root` отказывает в новых стадиях. Исключение — повтор упавшего узла с режимом `probe-and-reuse` или `idempotent-retry`.
- Второй прогон профиля, пока первый держит блокировку, завершается ошибкой `profile is already running`. Не удаляйте файл блокировки работающего процесса.

| Статус | Значение |
| --- | --- |
| `in-progress` | не все стадии пройдены |
| `failed` | стадия завершилась ошибкой; причина в `reason` |
| `rules-built` | выпуск собран и опубликован без баз |
| `workbench-run-passed` | одно поколение баз прошло все стадии |
| `workbench-ready` | прогон с `--baseline-result`: новое поколение баз дало побайтно тот же выпуск |

Прогон с `--baseline-result <result.json первого поколения>` завершается ошибкой `same generation`, если поколение хотя бы одной базы совпадает с базовым, и `release hashes differ from baseline generation`, если отличается SHA-256 хотя бы одного файла манифеста.

## Наблюдение

- Верхний уровень пишет `<run-root>/observation.jsonl`, а в `<run-root>/progress.txt` — текущую стадию (`stage:<имя>`).
- Каждая блокирующая команда (`reset`, `load`, узлы) идёт через общий адаптер наблюдения и пишет `<run-root>/stages/<стадия>/<роль или узел>/observation.jsonl`. Исполнитель передаёт адаптеру порог `limits.runtimeStageTimeoutSeconds`; если прогресс команды не меняется дольше порога, адаптер останавливает её, стадия получает статус `failed`, а `observation.jsonl` стадии — завершающее событие `failed` с причиной `stalled`.
- Команда стадии получает путь файла прогресса в `ONEC_OBSERVATION_PROGRESS_FILE`, путь результата в `KD_RULES_CYCLE_RESULT_FILE`, а также `KD_RULES_CYCLE_RUN_ID`, `KD_RULES_CYCLE_STAGE`, `KD_RULES_CYCLE_ROLE`. Команды `load` и узлов обязаны записать результат `{"status": "passed"}`.
- Контрольные точки в журнале регистрации базы содержат только `runId`, операцию, этап и результат: без данных базы, путей и учётных данных.
- Для разбора долгого или упавшего запуска используйте навык `1c-observe-run`.

## Узлы-расширения сценария

Прикладная стадия проекта объявляется в `scenario.json`:

```json
"nodes": [
  {
    "name": "apply-extension",
    "dependencies": ["load"],
    "inputs": ["src/cfe/ProjectExtension"],
    "outputs": ["apply.json"],
    "retry": "fresh-generation-required",
    "command": ["{python}", "migration/kd21/bin/apply_extension.py", "--result", "{resultFile}"]
  }
]
```

- `dependencies` — стадии или ранее объявленные узлы. Узел не запускается, пока зависимости не пройдены.
- `outputs` — файлы, которые команда создаёт в `{stageRoot}`; отсутствие файла — ошибка узла.
- `retry`: `probe-and-reuse` — узел с теми же входами, зависимостями и поколением баз не повторяется; `idempotent-retry` — узел можно запускать повторно, в том числе после его ошибки; `fresh-generation-required` — повтор в том же поколении баз запрещён, нужен `reset` в новом `run-root`.

## Правила написания алгоритмов КД 2.01

- **Параметры объекта.** `ПараметрыОбъекта` в алгоритмах КД 2.01 — индексируемый контейнер, а не `Структура`. Обязательный ключ читайте как `ПараметрыОбъекта["Имя"]`. Необязательный ключ читайте тем же индексным доступом внутри `Попытка ... Исключение ... КонецПопытки`; не вызывайте `ПараметрыОбъекта.Свойство`.
- **Режим совместимости.** Тексты обработчиков для конфигурации-источника пишите с учётом режима совместимости источника, для конфигурации-приёмника — режима совместимости приёмника: используйте только методы и синтаксис, доступные в каждом из этих режимов.

## Подтверждение алгоритмов и компилятора

- **Проверка исполнением.** Алгоритм считается подтверждённым только после исполнения сценария на целевой платформе (`load` и узлы сценария). Текстовая проверка или чтение кода подтверждением не считаются.
- **Изменение компилятора.** После изменения ядра или проектного слоя компилятора соберите выпуск на входах закреплённого эталона (`run build-rules` в новом `run-root`) и сравните его файлы и `manifest.json` с эталоном. Каждое отличие объясните принятым изменением до замены эталона. Необъяснённое отличие — возможный дефект компилятора: эталон не меняйте, разберите причину.

## Число прогонов и доказательства

- Один принимаемый прогон со статусом `workbench-run-passed` достаточен по умолчанию. Второе поколение (`--baseline-result`, статус `workbench-ready`) запускайте только по прямому запросу.
- Доказательства (`run-root`, выпуски, снимки, структуры) храните вне Git. Не коммитьте дампы, полные XML выпусков, журналы с данными и учётные данные.
- Если менялись стадии `reset`, `build`, `load` или `verify`, выполните один новый полный прогон: старые результаты не подтверждают изменённый механизм.
