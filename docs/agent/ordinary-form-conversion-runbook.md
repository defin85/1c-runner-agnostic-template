# Преобразование обычных форм EPF/ERF

Перед запуском установите в используемый Python 3.12+ пакеты `v8unpack` 1.2.6, `lxml` и `jsonschema`. Без них любая подкоманда `ordinary-form-conversion` завершается ошибкой `ModuleNotFoundError` до чтения входных файлов.

Этапы `analyze`, `convert` и `verify-remediation` работают без 1С. Этапы, которые получают выгрузку или собирают EPF/ERF (`prepare` и `prepare-sources` при выгрузке, `build`, `build-published`, `live-*`), вызывают `imported-skill epf-dump|epf-build -Profile <профиль>`. Цель берётся из имени профиля, поле `target` в профиле не нужно. Команда выполняется через `ibcmd` из профиля и пишет наблюдение в свой run-root; без доступной платформы такие этапы завершаются ошибкой, их результат считайте `not-run`.

Штатная точка входа:

```powershell
python -m scripts.python.cli ordinary-form-conversion analyze --input <файл.epf|дерево-v8unpack> --run-root <новый-каталог>
python -m scripts.python.cli ordinary-form-conversion analyze --input <файл.erf> --profile env/.local/<профиль>.json --run-root <новый-каталог>
python -m scripts.python.cli ordinary-form-conversion convert --input <вход> --profile env/.local/<профиль>.json --run-root <новый-каталог> --output <новый-каталог>
```

Для одного подготовительного вызова без ручного каталога запуска используйте `prepare`:

```powershell
python -m scripts.python.cli ordinary-form-conversion prepare --input <файл.epf|дерево-v8unpack> --profile env/.local/<профиль>.json --output <новый-пакет>
python -m scripts.python.cli ordinary-form-conversion prepare --input <файл.erf> --profile env/.local/<профиль>.json --output <новый-пакет>
```

Для нового EPF используйте отдельное получение канонической пары через Designer:

```powershell
python -m scripts.python.cli ordinary-form-conversion prepare-sources --input <файл.epf> --profile <профиль.json>
```

Результат: неизменённая Designer-выгрузка `src/epf/ordinary/<Имя>/`, отдельное рабочее дерево `src/epf/managed/<Имя>/` и сводка `.artifacts/ordinary-form-conversion/<run-id>/preparation-summary.json`. `v8unpack` разбирает только обычные `Form.bin`; XML-макеты копируются, объявленные `TemplateType=BinaryData` сохраняются. Команда завершается со статусом `agent-remediation-required` и не выполняет адаптацию BSL, проверку синтаксиса, сборку или запуск.

Если существуют `ordinary/<Имя>/`, `managed/<Имя>/` либо прежний `ordinary/<Имя>.v8unpack/`, команда ничего не заменяет. Переместите прежние ordinary и managed в резерв вне `src/epf/ordinary` и `src/epf/managed`, повторите получение из исходного EPF и сохраняйте резерв до ручного принятия новой пары. Автоматическое удаление не предусмотрено.

Команда создаёт самодостаточный пакет и останавливается до адаптации BSL:

```text
<новый-пакет>/
  source/                       нормализованный исходник
  managed/                      результат convert
    conversion-report.json
  preparation-summary.json     относительные пути, тип, хеши и следующий шаг
```

`canonicalRootHint` в сводке только подсказывает будущий корень `src/epf` или `src/erf`; команда туда не пишет. При `nextAction=resolve-structure` сначала устраняются структурные разрывы в `managed/`, при `nextAction=adapt-bsl` агент адаптирует модули из списка `modules`. Проверка синтаксиса, `verify-remediation`, сборка, публикация, запуск 1С и присвоение `ready` выполняются только отдельными командами и не входят в `prepare`.

После адаптации все последующие команды конвертера получают управляемый каталог пакета: `--output <новый-пакет>/managed`, а не корень `<новый-пакет>`.

`convert` сохраняет исходный BSL побайтно и поэтому всегда оставляет результат в `agent-remediation-required`. Агент сначала полностью переносит BSL на управляемую форму по карте процедур и обработчиков, меняя только копию `Module.bsl`. `verify-remediation` проверяет структурный план и привязки, но не синтаксис BSL. Синтаксис изменённых модулей проверяет `bsl-analyzer` с точным подключением целевой ИБ (см. раздел «Регистрационные сведения БСП»); сборка подтверждает только упаковку EPF/ERF.

Клиентские обработчики оставляют только интерфейс, локальные файлы и клиентскую автоматизацию. Обращения к глобальным менеджерам конфигурации (`Перечисления`, `Справочники`, `Документы` и аналогичным) выносятся в минимальные серверные функции; проверка модуля должна охватывать клиентский и серверный контексты целевой ИБ.

Если обработчик обычной формы вызывает экспортную функцию объекта без явного получателя, клиентский обработчик управляемой формы получает результат от минимальной серверной функции, серверная функция вызывает метод через `ОбработкаОбъект`, а показ результата остаётся на клиенте. Клиентские диалоги (`Предупреждение` и аналогичные) в модуле объекта заменяются по фактическому вызовному пути на серверно-допустимый результат либо содержательное исключение. Конвертер продолжает копировать BSL механически и не угадывает такие смысловые замены.

До контрольной сборки сопоставьте с обычной формой поддерживаемые свойства представления: отдельные надписи и заголовки полей, видимые рамки, пользовательские подписи и расположение команд, события формы и начальные значения. Неоднозначность оставляйте как `manual`, а не заменяйте техническим именем. `metadata verify` проверяет структуру скомпилированной формы; фактический вид подтверждает оператор отдельным открытием кандидата. Отсутствие такой живой проверки не блокирует передачу собранного кандидата, но не позволяет присвоить ему `ready`.

Пару дат и отдельную кнопку старого редактора периода переносите одним реквизитом `СтандартныйПериод`: синхронизируйте `ДатаНачала`/`ДатаОкончания` с объектом и удалите устаревшие кнопку и обработчик. В заголовке поля не сохраняйте завершающее двоеточие — платформа добавляет его сама. Горизонтальные технические строки задавайте с `ShowTitle=false` и без вертикального растяжения. Если поля обычной формы начинаются на одной координате, сохраняйте отдельные подписи одинаковой ширины; не смешивайте встроенный заголовок одного поля с отдельными подписями соседних строк. Поле с обработчиком `StartChoice` должно иметь видимую кнопку выбора. Панель, однозначно примыкающую к таблице, размещайте в её `AutoCommandBar`; команды отметки всех строк и снятия отметок показывайте через `StdPicture.CheckAll`/`StdPicture.UncheckAll` без текста, сохраняя обработчики, если вид таблицы не поддерживает соответствующие стандартные команды. Признак основной кнопки сохраняйте через `DefaultButton`; при неоднозначности оставляйте свойство для ручной адаптации.

Недоступные в тонком клиенте типы обычного приложения, включая `ПостроительОтчета` и `ОписаниеИсточникаДанных`, не оставляйте в клиентских процедурах: зависимую операцию переносите на сервер.

Начальные значения формы задавайте в `ПриСозданииНаСервере` (событие `OnCreateAtServer`). Туда же переносите операторы тела модуля обычной формы, код её `ПередОткрытием` и те действия `ПриОткрытии`, которые заполняют реквизиты, настраивают элементы (списки выбора, доступность, `СвязиПараметровВыбора`) или вызывают сервер; дату берите из `ТекущаяДатаСеанса()`, значения по умолчанию — из `БухгалтерскийУчетПереопределяемый.ПолучитьЗначениеПоУмолчанию`. В `ПриОткрытии` оставляйте только клиентские действия: клиентские переменные модуля, диалоги, локальные файлы. Конвертер переносит лишь назначение обработчика `ПриОткрытии` обычной формы и не переносит тело модуля, поэтому после адаптации сверьте в `metadata inspect` события формы с процедурами модуля: у каждого события есть процедура, у каждой процедуры-обработчика формы есть событие. Назначение события меняйте через `form.edit` (`formEvents`) и `form.remove-event`. Если план отклонён из-за повторяющихся имён элементов, сначала переименуйте повторы через `form.rename-element`.

## Регистрационные сведения БСП

В том же шаге `adapt-bsl`, до контрольной сборки, модуль объекта managed должен содержать экспортную функцию `СведенияОВнешнейОбработке`. Размещайте её среди определений процедур и функций, до первого оператора тела модуля. Если функция уже есть, не добавляйте вторую и не заменяйте её шаблоном: сверьте и исправьте только расхождения с назначением артефакта. Механическая подготовка и конвертер сохраняют исходный модуль, но не создают регистрационные сведения по имени или расширению файла.

Авторитетный контракт берите из модулей `ДополнительныеОтчетыИОбработки` и `ДополнительныеОтчетыИОбработкиКлиентСервер` фактической целевой конфигурации. `epf-bsp-init` служит только кратким образцом. Заполните понятное непустое `Наименование`, фактический `Вид`, версию артефакта и остальные обязательные поля целевого API. `БезопасныйРежим` не отключайте без обоснования используемыми возможностями. `Назначение` и команды добавляйте только когда их требует выбранный вид и реальный вызовный путь.

Три типовых примера не ограничивают остальные поддерживаемые БСП виды:

| Сценарий | Регистрационные сведения |
|---|---|
| Самостоятельная обработка с открытием формы | `Наименование = "Массовая выгрузка сканов"`; `Вид = ДополнительныеОтчетыИОбработкиКлиентСервер.ВидОбработкиДополнительнаяОбработка()`; команда использует `ТипКомандыОткрытиеФормы()` того же модуля |
| Самостоятельный отчёт | `Наименование = "Отчёт по договорам"`; `Вид = ДополнительныеОтчетыИОбработкиКлиентСервер.ВидОбработкиДополнительныйОтчет()`; команда добавляется только если её требует фактический маршрут отчёта |
| Печатная форма документа | `Наименование = "Акт инвентаризации ИНВ-17"`; `Вид = ДополнительныеОтчетыИОбработкиКлиентСервер.ВидОбработкиПечатнаяФорма()`; `Назначение` содержит фактическое имя документа, команда и серверный обработчик соответствуют контракту печати целевой БСП |

Содержательные значения подтверждает обзор вызовного пути и API целевой БСП. Добавляемые вручную контекстные директивы записывайте в точном синтаксисе BSL с обязательным символом `&`, например `&НаКлиенте` и `&НаСервере`. Синтаксис каждого изменённого модуля EPF/ERF подтверждает только `bsl-analyzer` с точным подключением целевой ИБ: её основной конфигурации и загруженных в неё расширений. Используйте штатную команду проекта для внешних артефактов, если она есть (в проекте с навыком `1c-check-bsl` — `make analyze-bsl-external EXTERNAL_ARGS='<Имя|каталог managed>'`). Ожидаемый результат: проверены только модули выбранных артефактов, при любом `ParseError` команда возвращает ненулевой код с путём модуля и текстом ошибки. Каталоги `ordinary/` не проверяются: это неизменяемая Designer-выгрузка исходной обработки, а модули обычных форм ERF лежат внутри `Form.bin`. `bsl-analyzer-workspace execute(check)` для модулей EPF/ERF не используйте: он не принимает модули с объявлениями процедур и директивами компиляции. Python, shell, регулярные выражения, текстовые маркеры, сборка и обратная выгрузка проверку не заменяют. Если BSL изменён после проверки или сборки, прежние доказательства и кандидат больше не актуальны — повторите проверку и сборку. Если авторитетная проверка недоступна, передайте исходники только с отметкой `синтаксис: не проверен`; запуск клиента, регистрация в БСП и живая проверка для этого этапа не требуются.

При содержательной адаптации заменяйте обычную пару дат и отдельную кнопку настройки единым формовым реквизитом `СтандартныйПериод`, синхронизируя его с датами объекта и удаляя устаревшие `НастройкаПериода`, кнопку и обработчик. До сборки на каждой странице сверяйте с обычной формой подписи флажков, контейнеры связанных полей и пояснений, командную панель каждой кнопки, картинки команд без текста и признак основной кнопки; действия табличной части размещайте в автокомандной панели самой таблицы. Замены общих модулей и сигнатур проверяйте по исходникам фактической целевой конфигурации. Не используйте необъявленные идентификаторы как выходные параметры `Свойство()` и аналогичных методов: объявляйте значение заранее либо после проверки наличия читайте свойство напрямую. Типы обычного приложения, недоступные в тонком клиенте, не переносите механически в клиентский код: минимальную зависимую операцию выполняйте на сервере.

```powershell
python -m scripts.python.cli ordinary-form-conversion verify-remediation --output <каталог> --run-root <новый-каталог>
python -m scripts.python.cli ordinary-form-conversion build --output <каталог> --profile env/.local/<профиль>.json --artifact <новый-файл.epf|erf> --run-root <новый-каталог>
```

После чистой проверки BSL и контрольной сборки канонические исходники публикуются отдельной командой:

```powershell
python -m scripts.python.cli ordinary-form-conversion publish-sources --input <исходный.erf|дерево-ExternalReport> --output <проверенный-каталог> --run-root <новый-каталог>
```

Для EPF `publish-sources` запрещён и направляет к `prepare-sources`; прежний маршрут сохранён для ERF. Существующие цели не перезаписываются. Команда `convert` по-прежнему не пишет в `src/**`.

Повторная сборка выполняется из опубликованного управляемого дерева и получает фиксированный локальный путь `.artifacts/epf/<Имя>.epf|erf`:

```powershell
python -m scripts.python.cli ordinary-form-conversion build-published --output <проверенный-каталог> --profile env/.local/<профиль>.json --run-root <новый-каталог>
```

Команда проверяет отпечаток `src/epf/managed/<Имя>/`, собирает конкретный опубликованный объект и фиксирует SHA-256 полученного файла. Бинарные хеши разных сборок не сравниваются.

Перед сборкой автоматически запускаются `metadata verify` и `metadata inspect` для точного внешнего объекта и его форм; сборка делегируется `epf-build`/`erf-build`. В отчёте сохраняются прежние ключи `form-validate`/`form-info` для чтения исторических результатов, но новая приёмка и публикация требуют свежей проверки с `engine=metadata`. Старый `passed` не заменяет её. Существующий вход, выход, артефакт, `src/**` и локальные профили не перезаписываются.

Ручную визуальную и поведенческую сверку выполняет оператор. Для цели из профиля запуск разрешается только явным `--allow-current-target`; подтверждение принимает путь к сохранённому снимку или иному файлу доказательства и фиксирует его SHA-256. Статус `ready` устанавливается отдельной командой только для совпадающих профиля, цели и хеша артефакта:

```powershell
python -m scripts.python.cli ordinary-form-conversion live-start --output <каталог> --profile env/.local/<профиль>.json --artifact <файл> --run-root <новый-каталог> --allow-current-target
python -m scripts.python.cli ordinary-form-conversion live-confirm --output <каталог> --profile env/.local/<профиль>.json --artifact <файл> --run-root <новый-каталог> --process-id <pid> --evidence <файл-доказательства>
python -m scripts.python.cli ordinary-form-conversion live-confirm --output <каталог> --profile env/.local/<профиль>.json --artifact <файл> --run-root <новый-каталог> --allow-manual-acceptance --evidence <файл-доказательства>
python -m scripts.python.cli ordinary-form-conversion ready --output <каталог> --profile env/.local/<профиль>.json --artifact <файл> --run-root <новый-каталог>
```

До `ready` любой собранный файл является кандидатом на проверку, а не готовым результатом. Адаптированные рабочие файлы для текущей задачи складываются в каталог `адаптированные` рядом с исходными файлами пользователя только без перезаписи существующего файла.
