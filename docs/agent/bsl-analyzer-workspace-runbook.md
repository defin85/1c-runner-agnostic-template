# BSL Analyzer workspace

Проект использует один MCP-сервер `bsl-analyzer-workspace` для анализа исходников и работы с несколькими ИБ. Не добавляйте отдельный MCP-сервер на каждую базу: подключение выбирается параметром `connection` живого инструмента.

Порядок выбора `search`, `symbol_info`, `graph`, `metadata`, `diagnostics` и живых инструментов задан в [регламенте поиска](repository-search-runbook.md).

## Запуск

- Команда сервера: `make bsl-analyzer-mcp` (`./scripts/platform/bsl-analyzer-mcp.sh`, на Windows — `.ps1`). Её указывают в конфигурации MCP агента.
- Исполняемый файл: `BSL_ANALYZER_EXECUTABLE` или `bsl-analyzer-app` из `PATH`.
- Исходники: первый существующий каталог с `Configuration.xml` из `BSL_ANALYZER_SOURCE_CANDIDATES` (через разделитель путей ОС; по умолчанию `src/cf`). Каталог должен быть внутри репозитория.
- Сервер работает в режиме брокера (`BSL_MCP_BROKER=1`): несколько клиентов одного репозитория используют один процесс и один базовый индекс; простаивающий брокер завершается через `BSL_MCP_IDLE_TTL_SECS` (по умолчанию 1800 секунд).
- Профиль embedding читается из `BSL_ANALYZER_EMBEDDING_ENV` (по умолчанию `~/.config/bsl-analyzer/embedding.env`), затем из `.env` репозитория.

`search`, `graph`, `metadata` и `diagnostics` строятся лениво и могут временно вернуть `loading`. Это не пустой результат: повторите вызов после готовности. Не запускайте отдельную индексацию на каждую сессию.

## Полный анализ BSL: `make analyze-bsl`

`make analyze-bsl` (Windows: `./make.ps1 analyze-bsl`) запускает тот же MCP-сервер, что `make bsl-analyzer-mcp`, запрашивает инструмент `diagnostics` для каждого модуля `.bsl` дерева исходников и завершается с кодом 1, если есть диагностика без точного исключения. Другого анализатора BSL шаблон не поставляет.

- Дерево исходников: `BSL_SRC_DIR` или тот же каталог, который индексирует сервер (`BSL_ANALYZER_SOURCE_CANDIDATES`, по умолчанию `src/cf`). Каталог должен быть внутри репозитория.
- Если не найден `bsl-analyzer-app`, реестр подключений или каталог с `Configuration.xml`, команда завершается с ошибкой `bsl-analyzer is not configured` и ссылкой на этот документ. Реестр без подключений (`{"connections": {}}`) достаточен для анализа.
- Ожидание ответа сервера ограничено `BSL_ANALYZER_MCP_TIMEOUT` (по умолчанию 180 секунд). При завершении команда закрывает stdin сервера, через 2 секунды останавливает всё дерево его процессов: группу процессов на Linux, Job object на Windows.
- `BSL_ANALYZER_REPORT=<путь.json>` сохраняет отчёт: версию анализатора, ревизию git, все диагностики и сводки по файлам, правилам и важности.
- `BSL_ANALYZER_MCP_BIN` задаёт другой запускатель сервера (`.py`, `.sh`, `.ps1` или исполняемый файл).
- `BSL_ANALYZER_MODE=standalone` вместе с `BSL_ANALYZER_REPORT` анализирует небольшое дерево командой `bsl-analyzer-app analyze` без резидентного сервера.

Точные исключения хранятся в `bsl-analyzer-exceptions.json` в корне проекта (другой путь — `BSL_ANALYZER_EXCEPTIONS`). Каждая запись описывает одну диагностику и ссылается на разобранную находку (`finding` в виде `ПРЕФИКС-номер` латиницей); `fingerprint` — SHA-256 от JSON с полями `path`, `line`, `rule`, `message`:

```json
{
  "schemaVersion": 1,
  "exceptions": [
    {
      "finding": "EX-001",
      "path": "src/cf/CommonModules/ОбщийМодуль/Ext/Module.bsl",
      "line": 12,
      "rule": "UnusedLocalVariable",
      "message": "<текст диагностики>",
      "fingerprint": "<sha256>"
    }
  ]
}
```

Исключение, которому больше не соответствует ни одна диагностика, делает проверку неуспешной: удалите или обновите запись. Если диагностики только сместились по строкам, `BSL_ANALYZER_REFRESH_RELOCATED_EXCEPTIONS=1` переписывает номера строк; при изменении правил или текста диагностик обновление отклоняется.

## Реестр подключений к ИБ

Локальный реестр: `env/.local/bsl-onec-connections.json` (другой путь — `BSL_ONEC_CONNECTIONS_FILE`). Реестр не коммитится. Он содержит URL HTTP-сервиса анализатора, имена переменных окружения и `allow_execute`; секреты задаются только в `.env` или окружении.

Запись с явными переменными:

```json
{
  "connections": {
    "dev": {
      "url": "http://127.0.0.1/<публикация>/hs/bsl-analyzer",
      "user_env": "BSL_ONEC_DEV_USER",
      "password_env": "BSL_ONEC_DEV_PASSWORD",
      "allow_execute": false
    }
  }
}
```

Запись с runtime profile:

```json
{
  "connections": {
    "dev": {
      "url": "http://127.0.0.1/<публикация>/hs/bsl-analyzer",
      "profile": "env/local.json",
      "allow_execute": false
    }
  }
}
```

Для записи с `profile` лаунчер берёт пользователя из `infobase.auth.user` профиля и имя переменной пароля из `infobase.auth.passwordEnv`. Пользователь передаётся анализатору через переменную `BSL_ONEC_USER__<ИМЯ_ПОДКЛЮЧЕНИЯ>`. Так профиль остаётся единственным источником параметров доступа к базе.

Правила реестра:

- `profile` нельзя совмещать с `user_env`/`password_env`; такая запись отклоняется.
- Поле `password` в реестре запрещено.
- Подключение попадает в сервер, только если доступны все его переменные; остальные пропускаются без ошибки.
- Лаунчер передаёт анализатору временную копию реестра без значений паролей и удаляет её после завершения.

## Выбор ИБ

Передавайте `connection` в `metadata`, `query`, `execute` и `event_log`, например:

- `metadata(action=tree, mode=infobase, connection=dev, filter=Константы)`;
- `query(action=execute, connection=dev, query="ВЫБРАТЬ 1 КАК Значение")`;
- `event_log(connection=dev, limit=20)`.

Для `metadata` в режиме `infobase` передавайте каноническое имя коллекции (`Documents`, `Catalogs`, `AccumulationRegisters`).

`execute(action=check)` проверяет BSL через ИБ. `run` и `eval` выполняют код и разрешены только при `allow_execute=true`. Включайте флаг только для изменяемых рабочих баз, явно разрешённых для выполнения кода; не включайте его для демонстрационных и аналитических баз. После правки реестра переподключите MCP-сервер, иначе он продолжит отвечать «BSL run is disabled».

## Живая отладка

`debug` подключается к штатному HTTP-серверу отладки платформы по `/e1crdbg` и требует `host`, `port`, точное имя регистрации ИБ, `config_root` и корни загруженных расширений. Исходники должны соответствовать загруженной конфигурации и расширениям: точки останова адресуются по идентификаторам метаданных и номерам строк. Включение HTTP-отладки на сервере 1С меняет настройки службы и требует отдельного разрешения.

## Установка сервиса анализатора в ИБ

HTTP-сервис анализатора ставится в ИБ как расширение через штатную обёртку загрузки расширения (`./scripts/platform/load-cfe.sh`) и публикуется через `make publish-http`. Если конфигурация в своём режиме совместимости не поддерживает расширения или не публикует HTTP-сервис расширения, сервис внедряется в основную конфигурацию отдельной согласованной процедурой с резервной копией `.cf`.

Восстановление базы из снимка удаляет расширения, которых нет в снимке: после восстановления установите сервис повторно и проверьте `/version`.

## Проверка

```bash
python -m unittest tests.python.test_bsl_mcp_runtime tests.python.test_bsl_connections
make verify-python-tests ARGS="tests/python/test_bsl_analyze.py"
./scripts/qa/check-bsl.sh --mode fast <модуль.bsl>
curl -u 'пользователь:пароль' http://127.0.0.1/<публикация>/hs/bsl-analyzer/version
```

После перезапуска агента в списке инструментов должен быть один набор: `metadata`, `query`, `execute`, `event_log`, `debug`, `search`, `graph`, `diagnostics`, `symbol_info`.

Языковой сервер редактора (`bsl-analyzer-app --stdio`) работает отдельно, MCP-сокет не использует и с брокером не конфликтует.

## Диагностика

- `404` — проверьте наличие сервиса в конфигурации или расширении и повторно опубликуйте ИБ.
- Неизвестное подключение — сверьте имя с локальным реестром.
- Подключение не появилось — проверьте, что заданы переменная пароля и (для явной записи) переменная пользователя.
- Запрещённый `run|eval` — штатная защита `allow_execute=false`.
