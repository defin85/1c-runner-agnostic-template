# Доработка metadata CLI

Repo script: `./scripts/python/run-python.sh`

Сначала воспроизвести конкретный отказ и установить различие с XML, который
формирует целевая платформа. Не подбирать свойства серией загрузок большого расширения.

1. Прочитать `metadata capabilities`, ближайший обработчик в
   `scripts/python/metadata_*.py` и его вызывающие места. Сохранить запрос,
   точную ошибку и evidence штатной операции. Различать импорт, проверку,
   применение к базе и фактическое поведение.
2. Использовать минимальное проверочное расширение проекта, если оно есть,
   или другой уже проверенный образец нужного типа. Проверить его соответствие
   основной конфигурации, платформе и режиму совместимости текущей задачи.
3. Если образца недостаточно, в разрешённой тестовой ИБ через Конфигуратор
   воспроизвести только проблемный объект: заимствование, необходимые свойства,
   признаки использования и контролируемости, один элемент или реквизит.
   Конфигуратор открывать только штатной обёрткой проекта; на Linux — по навыку
   [1c-designer-hidden-xpra](../1c-designer-hidden-xpra/SKILL.md).
   Выбирать профиль явно; навык не разрешает создание новой базы или применение
   диагностического расширения к данным. Сохранение конфигурации не требует её
   применения. Не редактировать рабочее расширение вместо проверочного.
4. Выгрузить сохранённый образец в новый каталог по навыку
   [1c-dump-src](../1c-dump-src/SKILL.md) с тем же профилем и явным именем расширения.
   В этом диагностическом сценарии читать XML напрямую допустимо: это эталон
   сериализации Конфигуратора для исправления CLI. Сравнивать смысл свойств,
   UUID-связи и состояния использования, учитывая перестановки XML платформой.
   Значения по умолчанию в редакторе не считать значениями основной конфигурации.
5. Исправить ближайший обработчик и, при новой возможности, предметную схему
   в `metadata_ops.py`. Сохранить общий `Snapshot` и `plan/apply`; не вводить
   параллельный XML-патчер. Добавить минимальный тест, воспроизводящий дефект,
   включая повторный план без изменения UUID и посторонних свойств.
6. Через исправленный CLI сформировать исходники и проверить их в точной
   платформе: применимость кандидата, а при разрешённом применении — живые
   свойства и обратную выгрузку. Успешный `verify` или сохранение в Конфигураторе
   не заменяет эти проверки. Если ошибка осталась, вернуться к образцу;
   не добавлять неподтверждённые зависимости в рабочее расширение.
7. Сохранить минимальный образец и краткое доказательство результата в репозитории,
   убрать собственные ненужные экспериментальные настройки через CLI и вернуться
   к исходной задаче по [metadata-use](../metadata-use/SKILL.md).

Проверочное расширение не включать в состав прикладной поставки. Для диагностики
загружать только явно выбранное расширение, не весь каталог `src/cfe`.
